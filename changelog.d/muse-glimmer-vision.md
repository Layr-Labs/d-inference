### Muse Glimmer 30B image input

- Muse Glimmer 30B takes OpenAI `image_url` parts on one Mac, always on with no switch. Discovery advertises `is_vision` for the two exact identities whenever the artifact passes its integrity checks: `config.json` declares the pinned vision stack, and `config.json`, `processor_config.json` and the index are the pinned revision's bytes, each read as a bounded regular file. The load builds the SDK image encoder from the installer's verified vision tensors with the configuration cross-checked; an advertised slot whose encoder does not load fails the load.
- Image requests keep the text route's prompt pipeline, parser, tool handling and stream. Each image renders as the template's one `<|patch|>`, decodes through the existing media limits (data URLs only), takes the grid of the reference processor (at most 4,096 merged tokens) and is expanded to `<|image_start|>`, its patches and `<|image_end|>`. Its features enter the engine as causal spans, so the 1,024-token prompt grid is unchanged; image prompts never reuse or publish the prefix cache, and the SDK never drafts beside them.
- Before any decode, the media memory gate reserves every image at its ceiling (4,098 prompt tokens, its features and one full-size tower run, an analytic bound until measured). A slot whose artifact fails an integrity check, video, an image outside a user message, a placeholder or size mismatch, and a required or named tool choice are refused with a typed 400 before any tower work. The client sees the closed code (`unsupported_media` or `invalid_media`) and its fixed message; the reason a slot refuses images is in the error's description and the Mac's log.
- Text requests are unchanged. No activation floor, measured-memory entry or catalog change is added.
