### Cluster link: each Mac proves the key its pair pinned

- On the link that carries a pair's prompts (`darkbloom cluster local` / `start --local --distributed`, and coordinator-formed pairs), each Mac now proves in every connection's handshake that it holds the Secure Enclave key the other Mac pinned: the key the pairing stored, or, for a coordinator-formed pair, the other member's key in the roster the coordinator verified. The pairing's edge secret alone no longer opens a connection with either Mac or lets anything in between take part in one; it stays a second factor. Each connection's keys still come from a fresh X25519 agreement.
- The link handshake is now version 3, with no fallback: a Mac on 0.10.12 (version 1) or on a DevNet build with version 2 can't join its pair until both Macs run this release; the refusal reads `protocolVersionMismatch`. A Mac that doesn't hold the key its pair pinned is refused (`peerNotPinned`, `identityMismatch`, `peerSignatureRejected`): pair the Macs again with `darkbloom cluster`.
- After a restart, until someone logs in to the Mac once, its key can't sign and the pair doesn't link (`localIdentityLocked`); it resumes by itself after the login.
- The setup exchange, model copies over the cable, GLM calibration's paired control and the pairing ceremony's own channel carry no prompt and keep the edge key alone, on the same version-3 handshake.
