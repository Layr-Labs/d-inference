### A cluster child gets its credential only if it runs the verified executable

- A pair's native worker, the coordinator member's local owner and the GLM calibration and quotation workers were hashed against their pins and then started by path. A binary replaced after the last check was started in their place and was written the data-plane credential (and the prefix-SSD key, then prompts). The provider now reads the code-directory hash (cdhash) of each arm64 image from the same bytes it hashes, starts such a child suspended, and before it runs any instruction requires the kernel's cdhash of its image to be one of them and Code Signing Services to find it valid. Only then is the child resumed and written to; otherwise it is killed and reaped without having run, and the launch fails with no path or hash in the message.
- An installed executable without a code signature is refused before it is started (release builds; arm64 binaries are always at least ad-hoc signed). Developer-ID and ad-hoc builds are checked alike.
