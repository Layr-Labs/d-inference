# Gemma assistant offload: source conclusion

A real registered assistant is available and can be constructed without the 26B target decoder. The root downloaded and verified its exact two-file artifact in `../assistant-artifact`; this audit did not read or hash the weight payload. The assistant is four layers, hidden 1024, conditioned by the target hidden 2816 and target shared K/V. `use_ordered_embeddings=false`: it computes its own full 262,144-token output head, rather than a small centroid head.

The assistant file payload is 236,127,665 B including configuration. Standalone target input embeddings require only three additional verified packed tensors, totaling 415,236,096 B. Combined stored payload is 651,363,761 B, before allocator, construction, attention, snapshot, graph or transport costs. A new additive selected loader and conditioning SPI are staged; they do not grant resource admission or install a native owner.

For the actual target geometry, capture layer 29 full attention and layer 28 sliding attention. At P4096, both K/V families together occupy 25,165,824 B in BF16: `[1,2,4096,512]` full K and V plus `[1,8,1024,256]` sliding K and V. P8192 raises the total to 41,943,040 B. New confirmed positions add 12,288 B of K/V data per token (4,096 full plus 8,192 sliding) before framing, packing, scratch or copies. The hidden is `[1,1,2816]` before final normalization; observe its actual dtype (5,632 B BF16 or 11,264 B F32). Carrying the selected embedding weights once avoids transferring target embeddings for every proposal.

The narrow parallel algorithm is a frozen-snapshot assistant chain. It may generate bounded proposals beyond a target window while the target GPU verifies that window. Stale conditioning affects proposal quality, not greedy target-prefix correctness, provided no proposal is published without actual target verification/commit. Full-prefix acceptance additionally requires the queued assistant continuation to cross the exact target bonus token; otherwise discard and reseed. A generic Foundation ledger implements this rule, credit bounds, one target window, cancellation and explicit retirement joins. Root independently compiled it and passed all 13 controls; this proves only the CPU control contract.

Existing `Gemma4CBv2MTPDrafter` already supports early submission but is a lazy in-process graph API with a local target identity. Network operations do not belong inside it. The staged additive branch uses its original absolute-position sliding mask and original assistant forward, while the root's existing owner/Collective performs serialized host consume/pull around actual asynchronous GPU work. No simultaneous P2P threads are needed. The target side must use the window-safe accepted-prefix transaction being implemented separately; the legacy rotating-cache trim path is insufficient at 4K.

The latest padded pair decoded at 32.010095 tokens/s versus its matched solo at 47.068303. An earlier timestamp solo reached 47.770422, so selecting the slower solo as a universal baseline would be misleading. The next fair test needs all three same-build arms: target-only, local assistant, remote assistant. The per-round target verification, non-overlapped transfer, reseed and uncovered drafting time divided by actual emitted target-confirmed tokens must beat the best applicable solo arm. Neither artifact size nor asynchronous control ordering predicts that result. No Gemma MTP numerical, remote or speed qualification exists from this audit.
