A closed, owned seven-tensor snapshot batch appears compatible with the pinned MLX completion model. I found no concrete dependency requiring a separate default-GPU stream fence after EVERY already-prepared CPU Send/Recv in this particular serialized snapshot path. This is a source-level conclusion with strict prerequisites, not permission to switch the current path or a completed lifetime/physical qualification. It is a smaller first experiment than packing if the new timers show snapshot synchronization matters: wire order, tensor bytes, per-transfer16MiB limits and existing allocation terms can remain unchanged.

The pinned evidence distinguishes three completion facts. C mlx_array_eval catches/returns evaluation failure and waits for the array's dependency event. transforms.cpp explicitly inserts inter-stream fences/events when scheduling CPU consumers of GPU producers. A ready array can nevertheless leave GPU command-buffer completion handlers holding input buffers; metal/eval.cpp captures those buffers until handlers run. GPU synchronize ends/commits the encoder, waits for the command buffer and checks its persistent error. The current implementation commits a new command buffer even when no additional model work was issued. That makes a repeated default-GPU fence potentially avoidable after one complete producer boundary, but C eval alone must not be relabeled a GPU retirement proof.

On the CPU side, Send::eval_cpu calls ensure_row_contiguous, sends the resulting buffer through the JACCL CPU adapter and returns an alias of the original input. A compact temporary is held by the CPU encoder and its release task until scheduled work completes. Recv::eval_cpu allocates its own output with no input graph. scheduler.cpp CPU synchronize queues a sentinel after previous tasks, waits and checks the stream error. cpu/eval.cpp schedules buffer/temporary release work in that same stream. Therefore every individual C eval AND CPU synchronize still matters; replacing them with a single final wait would change both failure and ownership behavior and is outside this design.

The existing receive ownership test is concrete: mlx_array_get_buffer_info uses array.is_donatable(), which requires both descriptor and data reference counts equal1, plus row-contiguous, zero-offset, exact data-elements and bounded allocation metadata in the Swift shim. Store received MLXArray object references without constructing native aliases. Validate each completed receive before any head concatenation, reshape/view, worker capture or batch-output vector holds another native reference. A final recheck before assembly is reasonable. Once assembly/views exist, uniqueness of the input allocations is intentionally lost; moving the original validation after that point is wrong.

Required sender sequence for a future private batch:

1. The original target attaches a bounded staging object and retains the capture before any new view construction or evaluation. Construct all seven ACTUAL send tensors first, including the four head slices. Evaluating only the five capture arrays is insufficient: the current loop creates lazy GPU-default slice primitives later.
2. Evaluate that vector of seven producer tensors with checked C status, then perform a checked producer GPU/CPU boundary. Keep the exact CPU/GPU stream handles for this operation. No new GPU/model/reshape/view work may occur between this boundary and batch completion; the check callback may only check resources, faults, deadline and owner state.
3. Send each tensor separately in the original seven-item wire order. Preserve every shape/type/peer check, C graph-construction status, C array-evaluation status, CPU synchronize status and check callback. CPU compact copies may still occur and retain the existing per-array charges. Retain the seven input views and resulting Send handles in the original staging object through the final batch fence.
4. At the batch boundary, perform checked GPU completion and the final owner checks before returning or allowing seeded ACK processing. The pending capture remains retained through the exact seeded ACK as today. Failure poisons the batch/channel and leaves staging under the original bounded failed-owner retention until actual retirement.

Do NOT vector-evaluate the seven Send or Recv graphs. Independent outputs have no network-order dependency and MLX's graph traversal may schedule them in a different order; these are blocking matched operations with different lengths. Only producer computation can be evaluated as a vector. The seven network operations must remain sequential, each with its own C eval and CPU completion.

Required receiver sequence: establish the same original-owner exclusive boundary, then receive the seven original shapes/dtypes in order. Attach each newly constructed C output to the original service's staging before evaluation, so a failed eval/fence cannot drop it through a local throw. Keep all seven roots; retain every C status and CPU completion/owned-storage test. No GPU consumer or concatenation is allowed during that receive phase. Perform the checked final batch GPU boundary before assembly/publication. Then run the existing two head concatenations and final capture evaluation/fences unchanged, retaining their outputs as the same ninth-root maximum. Worker installation and the exact seeded ACK continue to gate staging release. No callback, EOF or successful CPU receive substitutes for native or branch/process retirement.

The current per-call operationLock is not a model-work lock. A new batch must hold the existing shim serialization across its entire critical region AND be called only inside the original owner that forbids concurrent MLX work. It cannot recursively invoke current lock-taking sendCompleted/receiveCompleted while holding the same nonrecursive lock. The smallest implementation seam is private locked-batch entry plus internal already-locked operations, not a public fenceGPU=false flag. This proof does not extend to ordinary arbitrary model tensors, collective reductions, unrelated concurrent streams or calls whose check closure dispatches work. Existing generic APIs should keep their current fences.

This changes when GPU completion is observed. A conservative batch retains a checked entry producer boundary and a checked final boundary, and substitutes a fault/deadline/owner check at each old per-transfer GPU checkpoint so resource-observation cadence need not be silently reduced. Every actual CPU completion and every final GPU status remains checked. A failed GPU fence remains a failure, never a release proof. The independent process deadline still owns retirement if a native operation blocks; cancellation cannot interrupt a blocking backend by pretending an ACK happened.

Memory is favorable compared with packing. The seven Send handles alias their retained inputs; potential per-tensor compact copies are already individually covered by current senderAdditional terms. A receiver holding seven input tensors and then two assembled full tensors is exactly the current nine-root high-water enumeration. Deferring assembly does not exceed that simultaneous set. All named allocator bounds, maxima, snapshots, host metadata allowances and floors remain; no discount is inferred from this audit. The staging must retain native roots before failing C calls, not merely use withExtendedLifetime around a local variable. A small fixed array of references/metadata is additional host bookkeeping and must fit the existing bounded reserve.

Comparison with packing: both can reduce repeated GPU fences. An owned batch keeps seven network evaluations/CPU waits, but adds no large packed buffer, no new full-buffer alias pattern, no mixed-dtype conversion path and no changed shape cap. Packing can reduce network calls to1 at P128 or2 at P4K, at the cost of new packing/assembly storage and layout/ownership qualification. Delta conditioning changes later payload bytes but leaves initial seven-tensor shape; a future batch primitive could serve that path too only through a separately explicit five-item signature/ledger. None of these alternatives is a measured improvement yet.

Keep existing stale/cancel/ACK controls and original canonical lease/process/group cleanup. Compare same-build real-model rows/state/IDs before performance claims.
