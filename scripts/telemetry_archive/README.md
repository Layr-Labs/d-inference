# Copy-only telemetry snapshots

Capture complete bounded snapshots from a physical PostgreSQL read replica,
encode them as compressed Parquet, upload immutable objects to a private GCS
Standard bucket, and verify decoded contents and BigQuery query results.
This tool does not delete data, change retention, run migrations, create cloud
resources, or install a recurring job. Receipts explicitly say
`copy_only=true` and `retention_eligible=false`.

The telemetry tables are `request_profiles`, `fleet_snapshots`,
`request_rejections`, `inference_routes`, and `request_outcomes`. Accounting history
adds `usage`, `provider_earnings`, `ledger_entries`, and `provider_floor_draws`.
Balances, users, credentials, live payment workflows, and other tables remain rejected.
Accounting uses a separate bucket labeled `archive-scope=accounting` and an
`accounting_` BigQuery dataset. Mixed telemetry/accounting plans or destinations fail.
Route snapshots describe one database snapshot; they do not
claim to capture future outcome updates or every historical row version.

## Run

Use Python 3.12 and uv (CI uses 0.10.9):

```sh
cd scripts/telemetry_archive
uv sync --locked
uv run telemetry-archive --help
```

Provide `ARCHIVE_DATABASE_URL` through the environment, using a SELECT-only
role and a connection to the physical replica. The CLI has no primary bypass.
Every source transaction is repeatable-read and read-only with a 15-second
statement timeout, 1-second lock timeout, and 30-second idle timeout.
Use a Cloud SQL Auth Proxy or connector for connector-enforced instances.

```sh
uv run telemetry-archive capture \
  --table request_profiles \
  --start 2026-09-07T20:00:00Z --end 2026-09-07T20:01:00Z \
  --directory artifacts/profile-pilot

uv run telemetry-archive verify-local --directory artifacts/profile-pilot

uv run telemetry-archive upload \
  --directory artifacts/profile-pilot \
  --project darkbloom-mainnet --bucket YOUR_ARCHIVE_BUCKET

# Pass the receipt_uri returned by upload.
uv run telemetry-archive verify-remote \
  --project darkbloom-mainnet --receipt gs://YOUR_ARCHIVE_BUCKET/receipts/v1/ARTIFACT_ID.json \
  --bigquery --maximum-bytes-billed 1073741824
```

Cloud clients use Application Default Credentials. A local pilot can instead
supply a short-lived token through `ARCHIVE_GOOGLE_ACCESS_TOKEN`; never commit
tokens, database URLs, or production snapshot files. The container can use its
service identity. No secrets are accepted as command-line arguments.

The bucket must already exist, be private with enforced public access
prevention and uniform bucket access, use STANDARD in the requested region
(default us-east4), and have no lifecycle rules. Creation and IAM changes are
separate operations. An existing logs bucket with a deletion lifecycle is
deliberately rejected.

## What is verified

- COUNT and export use one source snapshot; insert/commit order and sparse IDs
  are never interpreted as completeness beyond that snapshot.
- Source records remain complete in `row_json`, generated by PostgreSQL's
  `row_to_json`, alongside their original PostgreSQL type catalog. Useful
  fields have typed Parquet projections; new columns remain in complete JSON.
- Accounting amounts and token counters are summed with exact integers in the
  same PostgreSQL snapshot, reconciled against decoded Parquet, and checked
  through BigQuery `BIGNUMERIC` sums. Receipts store totals as decimal strings;
  integer sums may exceed INT64. Stable accounting views expose INT64 amount
  and token fields plus account/request/settlement identifiers.
- Local readback checks schema, source count, ordered content SHA-256,
  individual row SHA-256, every projected value, time bounds, and file checksum.
- GCS writes use create-only preconditions, then download the exact generation
  and verify SHA-256. Same-artifact upload retries reuse identical objects;
  inconsistent existing objects fail without overwrite or deletion.
- The data object is verified before its file manifest is written. The remote
  receipt is written last. Partial runs have no successful receipt.
- Remote verification re-downloads and decodes the objects. BigQuery uses a
  temporary external table over the manifest-verified data URI and checks row count, distinct IDs,
  per-row payload hashes, time bounds, and ID/time extrema. No persistent
  BigQuery dataset/table is created; the query has a hard bytes-billed limit.

One snapshot is at most one hour within a UTC date. Defaults: 1,000 rows/page,
250,000 rows, 512 MiB raw JSON, and 120 seconds. Upper resource limits are
validated. Exceeding a bound or any query failure prevents receipt creation;
split the interval and rerun into a new directory. An existing local capture
directory is never overwritten. An interrupted local file is not a snapshot.

Different captures of the same window can contain late commits or updates and
receive different receipts. Query one receipt at a time. Do not wildcard-union
receipts and count overlapping snapshots as distinct events. This first
version has no automatic ongoing high-water mark.

## Resumable finite backfills

`prepare-plan` freezes explicit ranges for the allowed history tables.
`upload-plan` publishes its content-addressed plan in the existing bucket.
`run-backfill` processes non-overlapping hourly windows, splitting oversized or
timed-out captures down to at most one minute. A window that still fails stops
the run. Every completed leaf is independently uploaded and verified through
BigQuery before a create-only checkpoint is recorded.

```sh
uv run telemetry-archive prepare-plan --ranges ranges.json --output plan.json
uv run telemetry-archive upload-plan --file plan.json \
  --project darkbloom-mainnet --bucket darkbloom-mainnet-telemetry-archive
uv run telemetry-archive run-backfill --plan-id PLAN_ID \
  --project darkbloom-mainnet --bucket darkbloom-mainnet-telemetry-archive \
  --max-run-seconds 21000
```

`ranges.json` is an array of `{ "table": "request_profiles", "start":
"2026-09-03T21:00:00Z", "end": "2026-09-09T00:48:00Z" }` objects. Use actual
indexed source bounds. Each table may appear once, and each range is at most
365 days. Freeze the end explicitly; this is a finite historical copy.

The runner checks replica replay age before every new capture and exits with
code 75 when it reaches 30 seconds or the execution budget is exhausted.
Runtime budgets are checked between windows; the hosting platform must also
set its hard task timeout. This conservative replay-recency gate also stops a
caught-up replica if the primary has been quiet; receive/replay LSN equality does
not bypass it. No automatic service retry or schedule is created.
Rerun the same plan ID to resume. Saved data/manifest generations are checked
before skipping completed work. Persistent split decisions prevent overlapping
parent/child snapshots from entering the same completed coverage.

To observe the same ranges again after late commits or updates, prepare a plan
with a new explicit `--capture-generation`, for example `refresh-2026-10-05`.
The generation participates in plan identity; the same ranges/generation resume
the same checkpoints. Omitting it preserves existing version 1/2 plan identities.
This is manual recapture, not continuous change-data capture.

Only after every planned window is verified does the runner write
`backfills/v1/PLAN_ID/summary.json` and per-table `catalogs/TABLE.json` files.
The catalogs name the exact non-overlapping data files and generations; earlier
pilots and alternative snapshots are excluded. No source retention is involved.

Small completion catalogs retain their original inline `files` shape. Catalogs
that exceed the 2 MiB control-object limit instead use `format_version: 2`,
`file_count` and `shards`; each shard reference has a journal-relative `key`,
`file_count` and `sha256`. Read and verify those bounded shards to enumerate
files. Summaries are unchanged; publication continues to verify checkpoint
trees, so it does not depend on the completion catalog's representation.
The elapsed run budget also applies while replaying saved checkpoints and
finalizing catalogs; the new-window limit does not prevent finalizing a plan
that completed exactly that many new windows.

For a colocated Cloud Run Job, use its managed Cloud SQL socket and mount the
existing read-replica access JSON as a secret. Set `ARCHIVE_ACCESS_FILE` to the
mounted path and `ARCHIVE_EXPECTED_INSTANCE` to the exact replica connection
name. The adapter verifies that the credential names the expected instance,
and the source still enforces physical-replica and read-only checks. See the
[backfill launch runbook](../../docs/operations/telemetry-backfill.md) for the
separate infrastructure approval and resource scope.

## Accounting ID batches

Accounting tables also support `capture --table ledger_entries --id-start 1
--id-end 1001 --directory artifacts/ledger-pilot`, using an inclusive start and
exclusive end. Do not pass timestamp bounds with ID bounds. The source must
already have a valid single-column bigint primary key on `id`; the exporter
never creates an index or writes source SQL. Captures span at most 1,000,000
IDs and retain the same row/byte/time limits as timestamp snapshots.

ID ranges for `prepare-plan` contain `table`, `id_start`, and `id_end`.
Version 2 plans use 100,000-ID chunks and split oversized chunks down to one
ID; version 2 receipts preserve the ID bounds. Existing version 1 telemetry
plans, receipts, and Parquet envelopes remain readable. ID-based objects use
`id_range=START_END` directories; their timestamps need not be ordered or lie
within one day. Catalog `id_start`/`id_end` show ID coverage, while
`window_start`/`window_end` are null. Do not interpret this as time coverage.

Freeze bounds from indexed first/last-ID reads. Sparse IDs and a frozen upper
bound do not prove there are no late commits or later updates: each chunk is
an independently observed snapshot. Refresh explicitly identified ranges;
this is not CDC, a globally consistent financial backup, or deletion permission.
See [accounting history](../../docs/operations/accounting-history.md) for cloud setup.

## Test

```sh
uv run ruff check src tests
uv run ruff format --check src tests
uv run pytest -q
```

PostgreSQL integration tests run only when `TEST_ARCHIVE_DATABASE_URL` points
to a disposable local database named `archive_test`. They create test tables
there and refuse other hosts/database names. CI provides it. Tests cover
lossless JSON/numeric/Unicode restoration, new fields, consistent snapshots,
late commits, source failures, corrupt files, partial uploads, upload retries,
unsafe buckets, generation replacement, and BigQuery disagreement.

`uv.lock` pins local/CI resolution. The container uses `requirements.lock`,
generated with `uv export --frozen --no-dev --no-emit-project --no-header --format
requirements-txt --output-file requirements.lock`; keep them aligned.

See [the operator runbook](../../docs/operations/telemetry-archive.md).

## Catalog coverage and unique files

Coverage-format 2 keeps one catalog row per plan/window, including distinct empty
windows that share identical Parquet bytes. External manifests list each URI once;
reader queries group catalog observations per file before joining. `verified_windows`
and `data_files` are separate counters. Snapshot row/file sums still require overlap
reconciliation; they are not automatically distinct business rows.
Reusing a versioned BigQuery external table requires its manifest URI, external
configuration and inferred archive schema to match before any stable alias or
coverage pointer switches. A mismatched existing table stops publication.
Newly loaded and reused coverage catalogs are also read back: their exact schema,
physical row count and normalized coverage digest must match before publication.

The catalog digest includes a format-version domain and tables carry the label
`archive_coverage=plan_windows_v2`. Existing pinned workers keep their prior behavior.
After an approved image upgrade, republish every relevant plan from checkpoint trees
to restore empty-window coverage that older file-only catalogs collapsed. Importing
prior catalog rows alone cannot recover omitted intervals, and the new format label
is not a history-completion certificate. Raw files and old catalogs are preserved.

## Preview future analytics reads

`analytics-preview` compiles SQL by default. Add `--execute` for a SELECT-only
BigQuery check against one published catalog generation; it never changes a
view or the serving API. All inputs use the same explicit catalog version;
independently moving stable aliases are for single-table exploration only.
The output is explicitly shadow data with
`serving_eligible=false`, `retention_eligible=false`, and uncertified source
completeness. An empty result from an incomplete archive does not mean no
production activity occurred.

```sh
uv run telemetry-archive analytics-preview \
  --project darkbloom-mainnet --dataset accounting_history \
  --catalog CATALOG_VERSION --query leaderboard --metric earnings \
  --window 7d --as-of 2026-09-26T12:00:00Z
```

Queries: `leaderboard`, `network-totals`, `usage-timeseries`. Windows: `24h`,
`7d`, `30d`, `all` (execution of usage time series requires a finite window).
Leaderboard limits are 1–200. `--maximum-bytes-billed` defaults to 1 GiB and
cannot exceed 10 GiB; it caps both catalog and data queries. The client timeout
is 120 seconds. A timeout does not prove a server job has stopped; inspect the
BigQuery job before retrying. Financial sums serialize as exact decimal strings,
not floating-point JSON numbers. Preview files contain private account IDs and
must not be served publicly.

The [operational/history design](../../docs/design/operational-history-retention.md) and
`retention-policy.proposed.json` record the approved 5-minute public refresh
target and disabled 14-day completed-detail retention policy across telemetry
and accounting. The policy file is not runtime configuration. Existing receipts
cannot enable deletion; active state, financial fences and necessary transactional
counters remain operational. Continuous capture, broader table adapters, reader
migration and retirement remain separate qualification stages.

## Custom asynchronous queries

`query-submit` validates and submits an operator-authored SELECT over declared
`archive_<table>` CTEs pinned to one coverage-format-2 catalog. `query-status`
polls without waiting for running work and pages successful temporary results;
`query-cancel` requests cancellation of a tool-owned job. Explicit `archive-query-`
job IDs make retries idempotent. The commands never mutate source data or switch
published archive aliases. They are not an untrusted-user SQL sandbox.

See [historical query operations](../../docs/operations/history-queries.md) for
the SELECT example, command flags, access controls, limits and failure behavior.
No live deployment or query execution is implied by installing this CLI.
