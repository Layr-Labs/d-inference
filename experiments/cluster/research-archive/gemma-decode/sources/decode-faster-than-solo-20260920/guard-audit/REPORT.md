Each decode token has three completed sends and three receives per rank: five host controls and one model residual. New control APIs accept `Data` or an exact receive byte count, never `MLXArray`. The shim creates a fresh uint8 array by copying those bytes. The pinned Swift initializer calls the pinned C `mlx_array_new_data` path; C++ array initialization allocates and copies values without a producer primitive. The CPU Send/Recv backend and JACCL completed operations run on the selected CPU stream. CPU synchronization drains preceding work and completion cleanup before native ownership inspection. A control receive has no producer input or GPU consumer before copying its completed bytes to `Data`. Thus these five operations have no GPU dependency to fence. Generic tensor APIs still select both CPU and GPU fences; model residual call sites remain byte-identical.

The private common functions are the only functions that accept the fence selector. `RejectGPUArray.swift` and `RejectPrivateFence.swift` are expected compile-failure fixtures against the real implementation: a pending GPU array cannot enter the Data-only API, and callers cannot disable its GPU fence through the private helper. `ControlBounds.swift` invokes the actual implementation for twelve malformed send/receive sizes, before any MLX graph or collective access. These fixtures are staged, uncompiled and unexecuted. No mirrored implementation or fake collective qualifies the API. Full valid-frame behavior still needs the real matched two-rank run.

The omitted GPU fence is replaced with the same checked closure invocation. Expected logical guard cadence remains 65/63 per rank per decode token, including 195/189 environment visits. The holder still obtains one fresh observation at the start of each synchronous guard invocation and invalidates it on return; the two remaining environment visits validate that same invocation's observation. There is no cross-invocation snapshot cache. Padded frame geometry, residual fences, fault checks, clocks, ownership, 6/4/2 GiB floors and complete live-memory ledger are unchanged. The Data-return API now includes its existing host copy within the inclusive `wireReceiveCompleted` timing; total request/token clocks are unchanged. Do not interpret a change in that category alone as network cost.

The fresh power reader currently calls `IOPSCopyPowerSourcesInfo` and `IOPSGetProvidingPowerSourceType`, then obtains fresh thermal and low-power values, followed by Mach VM/pressure/swap observations. The gap between environment time and OS-snapshot time includes all these operations plus validation; it does not isolate IOPS. The pinned local IOKit SDK documents `IOPSGetTimeRemainingEstimate()` as returning `kIOPSTimeRemainingUnlimited` for external power without a time limit and `kIOPSTimeRemainingUnknown` when undetermined. Its scalar value offers a plausible fresh-call alternative. It is not yet measured or a runtime replacement. A missing snapshot, unknown estimate, nonfinite value or any value other than the unlimited constant must refuse; no retained power-source blob or notification cache is proposed.

`power-probe/ResourceGuardProbe.swift` is a separate Foundation/IOKit-only CPU probe. Every iteration brackets the fresh scalar call with two fresh legacy classifications, distinguishes observed transitions/unavailability/stable disagreements, and separately times both readers, thermal, low-power, fresh VM/pressure/swap, and combined environment reads. Seven inverse scalar cases reject unknown, finite-limited and nonfinite values. Timings include instrumentation overhead. The probe has an eight-second loop bound and ten-second hard alarm; root should use a fifteen-second owned process. It writes one report after measurement and never changes admission. A stable AC result on one host is not evidence of unplug/battery/UPS transition equivalence.

Root's next meaningful qualification is the source-pinned native build followed by one matched solo and lookahead cohort, exact token/full-row/whole-state equality, unchanged guard cadence/budget, and actual cleanup. The scalar CPU probe can run separately after compilation is granted. Any power replacement requires its own source review and actual agreement results; keep it out of the CPU-control candidate.
