# Long-running cluster service: next implementation boundary

These are root source-analysis notes, not implemented behavior or a qualification. The current HTTP host stores one immutable installed session. Its lifetime monitor tears down the listener when that session exhausts its request quota or reaches its fixed lifetime. `DistributedInstalledSession.canRotate` already requires actual release, but no replacement-session factory is connected to the HTTP host. This is the concrete reason the current delivery cannot yet claim long-running service.

The next bounded increment should retain the HTTP listener/discovery and rotate the owned session after a normal quota drain. Keep the existing short, bounded native incarnation, request UUID replay rules and canonical device exclusion. Do not implement this by raising the lifetime/request constants or clearing lease journals. It is acceptable for this first implementation to unload/reload between epochs, but its unavailable interval and load cost must be measured and reported; preserving resident weights across authenticated epoch renewal is a separate optimization.

Separate listener ownership, the currently advertised engine/tokenizer entry, and the retained session cleanup obligation. A focused rotation owner should receive a prepared-session factory pinned to the same installed configuration/artifact/capability; only one factory call/start can be pending. After closing admissions, wait for the exact old HTTP acquisition, response delivery, request retirement/resource release and old bridge shutdown. A new epoch may start only after both native retirements, authenticated owner releases and actual transport exits put the old session in released. Quarantine retains the old owner and prevents factory invocation. Model/config changes fail through existing preparation checks instead of silently substituting a new serving identity.

Each new engine entry must bind its new membership epoch. It cannot reuse the old engine's expected identity or let a late invalidation/stop callback retire a replacement entry. Bind monitor/teardown tasks to a generation and explicitly join the preceding generation's startup/stop. Stop during drain/load must prevent late publication; a partially started replacement remains retained for cleanup. The listener and discovery keep their stable identity across successful rotations, and failed rotations must stay observable through status with no advertised capacity.

Before the fixed lifetime expires, close admissions using the remaining request budget plus cleanup margin; an admitted request must retain its original deadline and be permitted to retire normally within that bound. Never extend a client deadline across reload. Requests during unavailable rotation should receive the existing explicit unavailable behavior; they must not be silently accepted into an unbounded queue. Whether and how to expose a retry hint must be checked against the existing HTTP/coordinator contracts, not invented inside the native layer.

Meaningful validation: actual model-free owner children across at least two quota boundaries; a held response/acquisition delays reuse; missing terminal or release ACK prevents next start; stop during replacement startup; late old-generation callbacks; preparation mismatch; exact fresh epoch identities and at most one owned native pair. Then run more than16 actual distributed requests through one listener, including an explicit5-minute lifetime boundary, and record unavailable/reload intervals, client deadlines, token correctness and actual cleanup. The physical series must remain separate from performance cohorts.

The network/coordinator path is another remaining integration boundary: current CLI distributed startup constructs the local server directly. A long-running local listener alone does not establish coordinator capacity, follower exclusion, billing or accounting correctness. Trace all capacity readers before integration, following root AGENTS.md.
