## ⚠ Required operator actions

These do **not** happen by deploying the binary.

### 1. Seed the per-model solo decode rate — STILL REQUIRED, as a cold-start floor

```
EIGENINFERENCE_MODEL_SOLO_TPS_SEED=gemma-4-26b-qat-4bit=14,gemma-4-26b-qat-4bit@M4|Max=70,gpt-oss-20b=30,gpt-oss-20b@M4|Max=70
```

Set on the coordinator VM's authoritative env file, **`/etc/d-inference/env`**.
`deploy/environments/prod.env` is a sanitized reference and changing it does not
change production. Human-approved per `AGENTS.md`.

**Do not delete this as redundant.** The durable fix landed in this release and
the seed is no longer what sets the steady-state cap — which makes it look
removable. It is not.

**What changed.** The coordinator's quality cap derives concurrency from a
static per-model solo decode rate. It now prefers the provider's own **measured**
rate — `observed_decode_tps`, which the provider already reports on every
heartbeat — over the model-agnostic `sqrt(memory_bandwidth)` proxy, even when
only one solo-gated sample exists. One uncontended heartbeat (~30 s) is enough
to move gemma-4 from the proxy's cap of **2** to the full reported **8**. No
wire change: the field was already populated and already ingested.

**Why the seed still has to be there.** Two independent reasons.

1. **Cold start.** A provider that has completed no request has no measured
   rate — its EWMA is 0 and `observed_decode_tps` is omitted from the
   heartbeat entirely. The TPS registry is also in-memory and restart-wiped, so
   every coordinator restart returns the whole fleet to that state. gemma-4 is
   a dedicated model (`EIGENINFERENCE_DEDICATED_MODELS=gemma-4`), so with no
   seed the chain lands on the `sqrt(memory_bandwidth)` proxy — ~23 tok/s on an
   M4 Max — and caps it at **2** until the first uncontended heartbeat lands.
   The seed removes that window across all ~94 boxes.
2. **It bounds cross-class transfer.** The seed is also the upper bound on
   solo medians borrowed from a *different* chip class, so observations from a
   faster tier cannot widen an unsampled slower tier's cap. Deleting the seed
   silently removes that ceiling too.

The seed value is now much less load-bearing — it is superseded within one
uncontended heartbeat — so it should stay conservative rather than accurate.

**It is also chip-class scoped, and must be.** A seed key may carry an
`@<ChipFamily>|<ChipTier>` qualifier (the coordinator's `chipClassKey`, the
same vocabulary the solo-sample store uses). The 70 tok/s figure is a
measurement of **one** class — the M4 Max gate box — and the fleet is
heterogeneous: the registry's own tests document gemma solo at 10–18 tok/s on
slower classes. Applied fleet-wide it would grant such a box cap 8 while it
decodes ~14 tok/s, projecting ~3.4 tok/s per request at that batch against the
15 tok/s floor. So 70 is scoped to `@M4|Max`, and every other class takes the
unqualified value (gemma 14 → cap 2; gpt-oss-20b 30 → cap 3).

A provider takes the entry for its own class when one exists, otherwise the
unqualified entry — which the coordinator additionally clamps to the slowest
class named for that model, so an unnamed class can never out-rank the slowest
named one. An unrecognized chip reports class `Unknown|Unknown` and therefore
always lands on the conservative unqualified value. If you add a class entry,
add it only for a class you have actually measured.

## Behaviour changes

### kv-quantization is retired

`darkbloom beta enable kv-quant` now exits 64 with
`Unknown beta feature 'kv-quant'. Available: mtp.` and leaves the config file
unmodified.

**Config loading never breaks.** A `provider.toml` carrying `kv_quant = true`
loads cleanly, keeps every other setting, and emits one retired-key warning; a
later config rewrite drops the key automatically. Verified end to end with the
real CLI binary against a config also carrying `memory_reserve_gb`,
`max_model_slots`, `idle_timeout_mins`, `engine_v2_kv_backend` and `mtp` — all
survived.

Quantized paged pages are planned as separate work after the paged migration.

### An explicit paged request now fails instead of silently degrading

Previously, if the paged kernel could not be served, the engine quietly fell
back to contiguous and logged it at INFO. It now depends on how paged was
selected:

| Selection | Preflight / capacity failure |
|---|---|
| `engine_v2_kv_backend = "auto"` (default) | falls back to contiguous, as before |
| `engine_v2_kv_backend = "paged"` (explicit) | **model fails to load** (503; the coordinator reroutes) |
| `DARKBLOOM_CBV2_PAGED_KV=0` (kill switch) | **always** falls back, never fails |

The kill switch keeps degrading on purpose: an operator disabling paged on a
fleet configured for paged must get service, not a 503 on every slot.

`darkbloom benchmark --kv-backend paged` follows the same rule and exits
non-zero if no cell could run, so a paged benchmark can never quietly report
contiguous numbers.

### `darkbloom benchmark --parity`: the Gate G2 check, on a real model

One command answers "is paged at parity with contiguous?". It loads a model
once, builds BOTH backends over the same weights, and reports each G2
criterion as PASS / FAIL / EXPECTED_SHORTFALL / UNAVAILABLE with the
measurement behind it: token exactness (raw sampled token IDs, greedy, must be
IDENTICAL — text equality is a weaker oracle and is not used), MTP token
exactness with proof that drafts were actually produced, packed prefill,
vision spans, and prefix reuse. JSON goes to stdout, the operator table to
stderr.

Capabilities are reported as EXECUTED, not as advertised. Packed prefill reads
`CBv2Engine.packedPrefillActivity()` and gates on the `groupsExecuted` counter
differenced across a batch of equal-length concurrent rows, never on
`isSupported` — a claimed-but-never-packed backend reports supported with zero
counters, the same shape as an inert MTP drafter. Vision spans are proven by a
real span submission surviving the backend gate. A capability the MODEL does
not claim reports UNAVAILABLE naming the model, never a backend fault.

```
darkbloom benchmark --parity --model <id> [--assistant-model <drafter-id>]
```

Three exit statuses, and the distinction is the point:

| Status | Meaning |
|---|---|
| 0 | at least one criterion was evaluated and none failed (EXPECTED_SHORTFALL is evaluated, and does not fail the run) |
| 1 | an evaluated criterion FAILED |
| 2 | nothing was evaluated — every criterion UNAVAILABLE |

A criterion that cannot be evaluated reports UNAVAILABLE **with the missing
prerequisite**, never PASS by default; and an all-skipped run does not exit 0,
because "the gate is green" and "the gate never ran" must not look the same to
CI. Verdicts are keyed on the RESOLVED backend, so a `paged` arm that degraded
is compared as contiguous and the report says so rather than reporting parity
with itself.

**EXPECTED_SHORTFALL** exists because paged pays one `maxWindow` of extra
frozen replay over contiguous by construction, so a hybrid model can never
reach `paged >= contiguous` on prefix reuse. Calling that FAIL forever trains
readers to skip the criterion; calling it PASS lets someone conclude the
backends match. It gets its own verdict, does not make the process exit
non-zero on its own, and is named in the summary line so it cannot be missed
in the tail of a CI log. The shortfall is reported as a **percentage of the
baseline's saving**, because the cost scales as `maxWindow / matched`: measured
at 128 of 26,880 tokens (0.5%) on gpt-oss-20b's 128-token window, and 1,024 of
2,816 (36%) on gemma-4's 1,024-token window. Negligible on short-window models,
severe on long-window ones. The allowance is one `maxWindow`, **not** one
prefill chunk — they coincide on neither model measured (gemma-4: window 1024
vs chunk 512; gpt-oss: window 128 vs chunk 512), so "one chunk" would
mispredict both. A shortfall LARGER than one `maxWindow`, or any shortfall
from a backend whose prefix-reuse capability derived unsupported, is a plain
FAIL.

Note it calls `EngineV2Factory.makeProductionBuild` directly and therefore
bypasses slot routing: every verdict is a statement about the BACKEND, not
about how production routes a slot to it.

### Compiled decode is removed

Incompatible with paged storage, and it had no B=8 rung — it fell back entirely
above B=4. Measured effect at B≤4 was roughly a wash (gpt-oss eager won by
~5%; gemma compiled won at B=2). `DARKBLOOM_CBV2_COMPILED` no longer exists.

### Memory: the activation reserve now scales with prefill shape

The flat 3 GiB reserve is replaced by a function of batch, query-block/span
width, context and heads. It only ever raises the old floor.

**Capacity impact:** boxes serving long-context vision will advertise less KV
headroom than before, because the old constant under-reserved for that case —
a 48 GiB box with 31 GiB of weights serving 100k-token VLM moves from 9.20 to
5.91 GiB of KV budget. This is a correction, not a regression: the previous
value was already wrong at B=4 for long contexts.

### Routing: the decode load factor is re-fitted

`effectiveTPSLoadFactor` moves 0.27 → 0.39, re-fitted against CBv2 measurements
(the old value came from a legacy engine on a dense 7B model and under-predicted
degradation by ~30% at B=8). This makes the concurrency cap slightly
**tighter**, and the warm-pool target and TTFT backlog estimates more accurate.

## Compatibility

- **Wire format is unchanged.** The `lossy_snapshot` prefix-cache outcome is
  retained on the wire and still decoded by the coordinator, even though no
  code path can emit it any more — pre-0.8.0 providers remain in the fleet
  during rollout.
- Mixed-version integration gates were repaired for this release; they had been
  failing since v0.7.15 and that compatibility was therefore unverified.
