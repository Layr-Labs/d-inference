### Gemma 4 system messages render as text parts on the local API, as vLLM renders them

- On the local API, a Gemma 4 26B request with a system (or developer) message now renders it as the chat template's text parts. Those parts end in a space before the system turn closes, as vLLM-served endpoints render every such request, so `usage.prompt_tokens` and the prompt the model reads match theirs (a GPQA-style prompt with the system message "You are a helpful assistant." is 88 tokens, not 87). List-shaped system and user content keeps its parts instead of being joined first, as Transformers renders it; the parts of a user list are trimmed one by one and join without a separator, as there.
- Network requests are unchanged in practice. Nearly every Gemma request the coordinator's prompt sidecar counts or plans, with or without cache routing, keeps the string prompt the sidecar renders, so cache receipts and deadline calibration still match. Only a network request the sidecar did not count (sampled out, throttled, or a sidecar error) renders the parts, so its count can differ by one from the same body counted by the sidecar. OpenRouter's GPQA count changes only when the sidecar renders the parts too. Media requests and other models are unchanged. `DARKBLOOM_GEMMA_SYSTEM_PARTS_RENDER=off` restores the previous render on a Mac.
