# Genuine control-only registration plan

This is a source plan and uncompiled private startup-mode implementation, not executed enrollment or proven eligibility. Existing actual observations show both target Macs have user-approved Darkbloom MDM enrollment. Their retained daemon snapshots are stale and lack `attestation_public_key`; an old self_signed status is not current trust. The exact target serials are G36VWKJ304 (24 GB) and MKJV9DJWDC (48 GB). The public attestation endpoint omits serial/UDID and cannot identify either by RAM/chip.

1. Root obtains an authorized read-only enrollment/store observation. Existing `mdm.Client.LookupDevice` uses `POST /v1/devices` with a serial filter to read enrolled device metadata, despite its POST method. Existing `GetMDAChainBySerial` selects the newest nonempty genuine chain. Record only exact target identity, chain/proof hashes and validity results; keep DSNs, MDM API credentials, auth tokens and private keys out of output. Do not issue SecurityInfo or DevicePropertiesAttestation merely to perform this read-only health check. Their existing scheduler callbacks are a distinct, later authorized live verification operation.
2. Configure a separate private coordinator store and real account/auth binding. Publish the actual signed private member release through the existing artifact-verification path; a loopback HTTP artifact origin is supported and avoids production catalog changes. Existing SyncBinaryHashes/SyncRuntimeManifest must supply current release/application evidence. A claimed version or KNOWN_BINARY_HASHES alone is insufficient. Preserve the same entitled persistent SE signing identity and real code-identity mechanism; do not mint an unrelated ephemeral key or seed Registry flags. The existing pair gate requires fresh CodeAttested/FreshCodeAttested as well as the SE/MDA/hardware evidence, so the real current code-attestation service must also be available.
3. Serve the same real Server handler over direct TLS with the separately qualified, explicit application CA option and exact hostname. The new explicit `native_shared_hardware_coordinator_v2` mode `trust_only` serves the same TLS Server with no NativePair catalog or selector. Its six exact fields are schema, mode, listenAddress, certificateFile, certificateSHA256 and keyFile; devices/approval/receipt are refused rather than ignored. The separate `one_request` mode keeps the reviewed one-grant path with its nine exact fields. These new mode sources and three command tests are included in the qualification wrapper but have not been compiled or run. With catalog nil, actual provider.go still registers cluster members, echoes their registration nonce, runs attestation/challenges and avoids NativePair Attach/Reserve; no native owner starts.
4. Start the actual signed member CLI in existing cluster-member role, using the original saved config, original signer and same ProviderLoop. Its role excludes preload/ordinary inference. Capture actual current registration IDs and the persisted public signer key, then bind serial + SHA256 of that exact key to the intended two devices. The registration ACK proves role/connection acceptance only, not hardware trust. Keep a bounded root-owned process fence and stop the control-only session without claiming native cleanup from a timer.
5. Allow the existing legitimate verification path to produce current hardware, MDA, SE-possession, heartbeat and code/release evidence. `attachCachedMDAProof` must re-verify the Apple-signed chain and expiry, and its FreshnessCode must equal SHA256 of this exact current SE public key; serial-only matches do not qualify. A fresh current challenge/application evidence must still be earned. Missing, expired, rotated-key or unavailable code proof remains an explicit refusal. Do not copy prior boolean flags, timestamps, release generations or public-feed reputation into the private store.
6. Only after that control-only evidence is accepted should root bind the two exact identities, actual final numerical runtime descriptor/policy/builds and signed CLI into the one-request catalog/config. A fresh connection has a fresh Provider ID; the driver selects by real serial/key and resolves actual current Provider objects, while original Reserve repeats all gates. Neither successful TLS nor the read-only enrollment result authorizes a native request.

Current source anchors: qualified workspace `coordinator/api/provider.go` registration around lines 427/609; `registry/verified_pair_membership.go`; `api/provider.go` stageDurableMDAChain/attachCachedMDAProof; `mdm/mdm.go` LookupDevice; `store/interface_domains.go`; original ProviderLoop+Trust and DaemonStateFile. All hardware/default ownership paths remain the existing ones. No production store mutation, trust-store workaround, custom accept-all TLS or standalone replacement owner is proposed.
