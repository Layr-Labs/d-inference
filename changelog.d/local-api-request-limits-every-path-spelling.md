### The local API applies its request limits to every spelling of a path

- A path with extra slashes (`/v1/chat/completions/`, `//v1/chat/completions`, `/v1//chat/completions`) resolves to the same route, but it skipped the local API's own checks and was served by the SDK's handler: no JSON nesting or NUL check, no 64-request batch bound and no tool-call `arguments` check. A caller with the local API key could therefore send a deeply nested body to parsers that run on a 512 KiB stack. Only Hummingbird's 2 MiB body ceiling held. Every spelling now gets its route's limits and answers.
- Such a spelling is also served as the exact path is: chat with the 32 MiB body ceiling, template controls and tool-schema `$ref` resolution, a request this Mac can't take passed on by the local router, and `/v1/models/` listing the router's merged models.
- The limits are now the default for every route instead of a list of paths. A request other than a GET, HEAD or OPTIONS to a route with no limits of its own (`/v1/responses/:response_id/cancel`, a route a later SDK adds, a path or method no route serves) is held to the 2 MiB body ceiling and the nesting check: over them it answers `413` or `400`, where it ignored the body or answered `404` before.
- A batch array behind a UTF-8 byte-order mark, which the JSON parsers skip, is counted like any other: over 64 requests it answers `batch_too_large` before any is decoded, where the count read it as no list and its requests were decoded first (requests that did not decode answered a decode `400`).
- Otherwise the limits, statuses and error bodies of the routes that already had them are unchanged on their exact paths, and nothing a coordinator sees changes.
