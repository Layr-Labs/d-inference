# Provider v0.8.0 — release notes

> **SUPERSEDED BY v0.8.1 — the paged default was reverted.** Everything below
> describes v0.8.0 as shipped and is left unedited as the record. What changed:
> `.auto` resolves **contiguous** again from v0.8.1. The paged pool is sized by
> `PagedKVPhysicalCapacityPolicy` rather than by the slot's logical grant, which
> summed to **1,137 GiB of fleet KV against contiguous's 11,453 GiB**; the
> resulting admission failures (32.7% of provider attempts returning
> `token_budget_exhausted`, TTFT p95 12.8s / p99 33s, ~8.8% of client requests
> cancelled before first token, OpenRouter-scored uptime ~85%) outweighed the
> throughput and adoption-exactness wins argued below. The adoption-exactness
> finding in this document is still correct and still load-bearing — v0.8.1
> answers it by NOT CONSTRUCTING the SSD prefix cache on a resolved-contiguous
> slot, so the wrong-answer class that made paged attractive is closed rather
> than reaccepted. Paged, the kill switch, the crash-loop guard and the blocking
> paged CI lane are all retained; `engine_v2_kv_backend = "paged"` still works.
> The batch raise to 8 is **not** reverted — it never depended on paged.

**v0.8.0 makes PagedAttention the default.** `.auto` resolves paged for every
model, the decode batch rises from 4 to 8, and kv-quantization is retired.
Rollback is one env var **per machine**: `DARKBLOOM_CBV2_PAGED_KV=0` in that
box's environment. There is **no fleet push channel** for env vars — a
fleet-wide rollback is a release (or ~94 hands on ~94 machines). Two
mitigations ship with that honestly stated: the **crash-loop backend guard**
automates the per-machine flip for the worst case (a paged defect that kills
the daemon flips that box to contiguous by itself after 3 crash-loop
restarts — see "Crash-loop backend guard" below), and per-machine operators
keep the env-var and per-slot `engine_v2_kv_backend = "contiguous"` levers.

Operator-facing changes in the PagedAttention migration. Added to as each track
lands; folded into `CHANGELOG.md` at release. Kept separate
from `CHANGELOG.md`'s `Unreleased` section deliberately — that section is
commit-derived and dated Apr 26 – May 25 2026, so a v0.8.0 entry would be
misfiled there.

Engineering detail lives in `JOURNAL.md` and
`docs/reports/2026-07-25-paged-kv-migration-plan.md`. This file is only what an
operator or a consumer needs to know.

## ⚠ Required operator actions

These do **not** happen by deploying the binary.

### 1. Seed the per-model solo decode rate — now SHIPPED, verify it landed

```
EIGENINFERENCE_MODEL_SOLO_TPS_SEED=gemma-4-26b-qat-4bit=14,gemma-4-26b-qat-4bit@M4|Max=70,gpt-oss-20b=30,gpt-oss-20b@M4|Max=70
```

This is no longer a hand-edit. The seed now ships in
`deploy/gcp/prod/release-env-defaults`, so `refresh-env.sh` installs it into the
authoritative **`/etc/d-inference/env`** on the next run, and
`deploy/gcp/prod/required-env-keys.txt` lists it so a coordinator env that lacks
it is rejected rather than quietly started. Value human-approved per
`AGENTS.md`.

For an entire release it existed **only** in `deploy/environments/prod.env`,
whose own header says it is not consumed directly — so it reached no
coordinator and every model was effectively unseeded. That file remains a
sanitized reference; editing it still does not change production. The two are
now pinned equal by `TestSoloSeedReachesProductionEnv`.

After deploying, confirm it landed:

```
sudo grep EIGENINFERENCE_MODEL_SOLO_TPS_SEED /etc/d-inference/env
```

**Do not delete this as redundant.** The durable fix landed in this release and
the seed is no longer what sets the steady-state cap — which makes it look
removable. It is not.

**What changed.** The coordinator's quality cap derives concurrency from a
static per-model solo decode rate. It now prefers the provider's own **measured**
rate — `observed_decode_tps`, which the provider already reports on every
heartbeat — over the model-agnostic `sqrt(memory_bandwidth)` proxy, even when
only one solo-gated sample exists. One uncontended heartbeat (~30 s) is enough
to move gemma-4 from the proxy's cap of **2** to the full reported **8**. No
wire change: the field was already populated and already ingested.

**Why the seed still has to be there.** Two independent reasons.

1. **Cold start.** A provider that has completed no request has no measured
   rate — its EWMA is 0 and `observed_decode_tps` is omitted from the
   heartbeat entirely. The TPS registry is also in-memory and restart-wiped, so
   every coordinator restart returns the whole fleet to that state. gemma-4 is
   a dedicated model (`EIGENINFERENCE_DEDICATED_MODELS=gemma-4`), so with no
   seed the chain lands on the `sqrt(memory_bandwidth)` proxy — ~23 tok/s on an
   M4 Max — and caps it at **2** until the first uncontended heartbeat lands.
   The seed removes that window across all ~94 boxes.
2. **It bounds cross-class transfer.** The seed is also the upper bound on
   solo medians borrowed from a *different* chip class, so observations from a
   faster tier cannot widen an unsampled slower tier's cap. Deleting the seed
   silently removes that ceiling too.

The seed value is now much less load-bearing — it is superseded within one
uncontended heartbeat — so it should stay conservative rather than accurate.

**It is also chip-class scoped, and must be.** A seed key may carry an
`@<ChipFamily>|<ChipTier>` qualifier (the coordinator's `chipClassKey`, the
same vocabulary the solo-sample store uses). The 70 tok/s figure is a
measurement of **one** class — the M4 Max gate box — and the fleet is
heterogeneous: the registry's own tests document gemma solo at 10–18 tok/s on
slower classes. Applied fleet-wide it would grant such a box cap 8 while it
decodes ~14 tok/s, projecting ~3.4 tok/s per request at that batch against the
15 tok/s floor. So 70 is scoped to `@M4|Max`, and every other class takes the
unqualified value (gemma 14 → cap 2; gpt-oss-20b 30 → cap 3).

A provider takes the entry for its own class when one exists, otherwise the
unqualified entry — which the coordinator additionally clamps to the slowest
class named for that model, so an unnamed class can never out-rank the slowest
named one. An unrecognized chip reports class `Unknown|Unknown` and therefore
always lands on the conservative unqualified value. If you add a class entry,
add it only for a class you have actually measured.

## Behaviour changes

### kv-quantization is retired

`darkbloom beta enable kv-quant` now exits 64 with
`Unknown beta feature 'kv-quant'. Available: mtp.` and leaves the config file
unmodified.

**Config loading never breaks.** A `provider.toml` carrying `kv_quant = true`
loads cleanly, keeps every other setting, and emits one retired-key warning; a
later config rewrite drops the key automatically. Verified end to end with the
real CLI binary against a config also carrying `memory_reserve_gb`,
`max_model_slots`, `idle_timeout_mins`, `engine_v2_kv_backend` and `mtp` — all
survived.

**Nothing about serving changes.** No provider ever served quantized KV —
v0.7.5 through v0.7.15 already served fp16-only and warned that the setting
did not apply — so memory footprint, KV capacity and advertised headroom are
identical whether or not the key was set. Quantized paged pages are planned as
separate work after the paged migration.

### An explicit paged request now fails instead of silently degrading

Previously, if the paged kernel could not be served, the engine quietly fell
back to contiguous and logged it at INFO. What happens now depends on how
paged was selected AND on what went wrong. The complete matrix — every
failure mode, honestly, including the one that is neither a degrade nor a
refusal:

| Failure mode | `"auto"` (default) | `"paged"` (explicit) | kill switch set |
|---|---|---|---|
| Kernel preflight fails | degrade → contiguous (`kernel_preflight: …`) | **refuse** (503) | degrade (`kill_switch`) |
| Physical-capacity plan refuses | degrade → contiguous (`physical_capacity: …`) | **refuse** (503) | degrade (`kill_switch`) |
| Layout paged-ineligible | degrade → contiguous (`ineligible: …`) | **refuse** (503) | degrade (`kill_switch`) |
| Pool construction throws | degrade → contiguous (`pool_construction_capacity: …`) | **refuse** (503) | degrade (`kill_switch`) |
| Malformed `DARKBLOOM_CBV2_PAGED_KV_DTYPE` | degrade → contiguous (`invalid_dtype: <the typo>`) — **changed in this release**; it used to refuse under `.auto` too | **refuse** (503, `paged_kv_dtype_invalid`) | knob never read (contiguous has no pages) |
| VLM slot whose paged cache can't vouch for span masks | forced contiguous, silently (policy veto, no fallback reason) | forced contiguous, silently | forced contiguous |
| Paged builds fine, **daemon crashes** at load / first decode | nothing above catches this — the watchdog restarts the box every ~5 min. After **3** consecutive crash-loop-shaped restarts the **crash-loop backend guard** trips: `.auto` resolves contiguous on that box (`crash_loop_guard`) | **not overridden** — explicit paged keeps crashing; operator intent beats automation | degrade (`kill_switch`) |

Every degrade names its reason on the heartbeat
(`kv_backend_fallback_reason`), in `darkbloom status` (per-slot posture
line), and in the once-per-load `engine_v2_kv_backend` telemetry event.

The kill switch keeps degrading on purpose: an operator disabling paged on a
fleet configured for paged must get service, not a 503 on every slot.

`darkbloom benchmark --kv-backend paged` follows the same rule and exits
non-zero if no cell could run, so a paged benchmark can never quietly report
contiguous numbers.

### Crash-loop backend guard: "if paged doesn't work we switch to contiguous", made true

A paged defect that kills the daemon (at model load, or mid-request — an
activation OOM is a daemon kill, there is no MLX error handler) used to be an
**unbounded ~5-minute crash loop**: the watchdog restarted the same binary
into the same paged default forever, and in-process engine recovery rebuilds
on the same backend. Nothing switched anything.

Now the watchdog counts consecutive **crash-loop-shaped** restarts — each
issued after the provider stayed up **less than 15 minutes** since the
previous restart. At **3**, it persists a guard record
(`~/.darkbloom/kv-backend-guard.json`: trip time, binary version, crash
count) *before* issuing the restart, and from that boot on `.auto` resolves
**contiguous** on that box, reported as `crash_loop_guard` everywhere the
other fallback reasons appear. Total downtime to self-heal: ~15–20 minutes,
against the unbounded loop it replaces.

The guard's edges, all deliberate:

- **Explicit config wins.** `engine_v2_kv_backend = "paged"` (global or
  by-model) is NOT overridden — automation never downgrades an explicit
  operator selection. The kill switch may, because it *is* an operator.
- **Clears on the next release, and only then (or by hand).** The record
  binds the binary version that tripped it; a new version reads it as inert
  and deletes it at daemon start. A release is the fleet's only fix-delivery
  vector, so "new version" is the retry signal. There is **no time-based
  retry** — "try paged again every N hours" would re-enter the crash loop
  daily. Manual: `darkbloom doctor --clear-backend-guard`.
- **The binary-rollback automation wins when both could act.** During the
  ~10-minute post-update stabilization window, 3 failed starts roll the
  *binary* back to the verified predecessor (which also fixes paged — the
  pre-0.8.0 predecessor resolves `.auto` to contiguous), so the backend
  guard stands down while a viable rollback is pending and steps in only if
  that rollback was refused.
- **Fail open.** A corrupt/garbage guard file reads as "no guard" and
  `.auto` resolves paged normally.
- **Visible.** Tripping emits an ERROR `engine_health` event
  (`operation=engine_v2_crash_loop_guard`) through the panic-hook transport
  (disk queue, shipped when the healed daemon reconnects); `darkbloom
  status` prints the guard with its age and trip version; `darkbloom
  doctor` reports it as a WARN check.

### `darkbloom benchmark --parity`: the Gate G2 check, on a real model

One command answers "is paged at parity with contiguous?". It loads a model
once, builds BOTH backends over the same weights, and reports each G2
criterion as PASS / FAIL / EXPECTED_SHORTFALL / UNAVAILABLE with the
measurement behind it: token exactness (raw sampled token IDs, greedy, must be
IDENTICAL — text equality is a weaker oracle and is not used), MTP
losslessness with proof that drafts were actually produced, packed prefill,
vision spans, and prefix reuse. JSON goes to stdout, the operator table to
stderr.

Capabilities are reported as EXECUTED, not as advertised. Packed prefill reads
`CBv2Engine.packedPrefillActivity()` and gates on the `groupsExecuted` counter
differenced across a batch of equal-length concurrent rows, never on
`isSupported` — a claimed-but-never-packed backend reports supported with zero
counters, the same shape as an inert MTP drafter. Vision spans are proven by a
real span submission surviving the backend gate. A capability the MODEL does
not claim reports UNAVAILABLE naming the model, never a backend fault.

**Token exactness is a PASS-ONLY signal.** It can confirm parity and never
accuse. Two measured reasons: the incumbent fails it too — contiguous against
CONTIGUOUS diverges on gemma-4 with no backend involved, purely by moving the
operator-reachable `DARKBLOOM_CBV2_ATTN_QUERY_BLOCK` knob from 128 to 8
(investigation at `977a5893e`). Reachable is the load-bearing word:
`AttentionV1` accepts any value >= 0 at runtime with no version gate, so no
policy change can close that path — and under this release's by-value split of
the knob, `128 -> 8` is a *supported* setting anyway; only `= 0` is
unsupported, for a memory reason unrelated to exactness. Retiring the knob
would not re-arm this gate either: it is the cheapest demonstration of the
sensitivity, not its cause. The second reason needs no knob at all: past the
FIRST flip the comparison is not well-posed, because the two arms are then
decoding different contexts and every later
position compares two unrelated conversations. So the report gives the first
flip per row, never a "divergence rate", and a divergence yields UNAVAILABLE
rather than FAIL. It remains a genuine gate on models whose argmax is stable:
gpt-oss-20b passes it outright.

**The MTP criterion scores each backend against ITSELF, and it can FAIL.**
It does not diff the two arms' MTP token streams against each other. That
form inherits whatever drift the base decode already has, and since base
decode divergence is a PASS-only signal, an MTP divergence on gemma-4 would
always have been written off as inherited — the criterion could never have
reached a FAIL on the model this release is about. Instead each arm's MTP
output is compared with that same arm's own plain greedy output. Verified
greedy speculation accepts a draft token only where it equals the target's
own argmax, so reproducing plain decode is definitional, not a tuning goal;
and both sides of the comparison share a backend, its kernels and its storage
order, so base-decode drift cancels instead of propagating. If the reference
arm is lossless and the candidate is not, that is an MTP defect on the
candidate backend and the run exits non-zero. If the reference arm is not
lossless either, the criterion reports UNAVAILABLE and says plainly that the
INCUMBENT failed the bar — never that the candidate was untestable.

One thing a PASS here does not mean: greedy argmax is a coarse detector, so
token-identical is not numerically identical. The natural hardening — carry a
numeric witness beside the tokens — is blocked for a measured reason, not an
oversight: requesting top-k logprobs on the MTP arm pulls rows off the
verification path back onto the sampler and the drafter stops engaging
entirely (rounds 5 to 0, drafted 5 to 0, on both backends), manufacturing the
exact silent no-op the criterion exists to catch.

The mechanism is **storage-order drift, amplified ~1,300x relative to gpt-oss**
by gemma-4's attention scale of 1.0 at head dim 256/512 and its MoE routing
density, landing on decisions whose margins are smaller than the amplified
perturbation. It is explicitly NOT "ulp-only": ULP-scale is the ORIGIN, not
the arrival. At the first flip the contested-vocabulary delta is 3.657 against
a 0.604 argmax margin — 6.1x, so it flips — while the prompt that holds
inverts the ratio (margin 4.508, delta 0.691, 0.15x). Single-layer deltas
decay with depth (layers 0-9 give 4.0-9.4; layer 29 alone gives 0.244), so the
arrival magnitude is amplification through 30 residual layers and 240
top-8-of-128 MoE selections. The divergence PREDATES this wave's ring shrink —
byte-identical at 97 pages — so nothing landed here caused it.

Each flip also carries the baseline's top1-top2 argmax gap against a floor
derived from the fp16 KV precision. Read that narrowly: it answers "was this
decision resolvable in the storage dtype" (on gemma-4, yes), not "was the
perturbation small".

**A same-backend control arm establishes that per run, not by assertion.** The
gate builds a third engine — paged with `DARKBLOOM_CBV2_PAGED_KV_DTYPE=float32`
— and re-runs the same prompts against the paged fp16 arm. Flipping the pool
dtype changes no algorithm, only storage precision, so if the tokens move the
model's argmax does not survive a benign perturbation and no cross-backend
token comparison on it is meaningful. Measured:

| model | control | token exactness |
|---|---|---|
| gemma-4-26B | NOT token-exact (2 of 3 rows flip at token 1) | UNAVAILABLE |
| gpt-oss-20b | TOKEN-EXACT over 144 tokens | PASS |

The control discriminates rather than always failing, which is what makes it
an instrument. On gemma-4 the same position yields three different tokens from
three configurations of the same weights — contiguous 100, paged fp16 107,
paged fp32 101. When the control fails, its headline LEADS the criterion's
detail, so a reader meets "the incumbent also flips here" before the
divergence it explains.

The arm is trusted only when `ProductionBuild.pagedPoolDType` confirms fp32
actually served, and only when no row hit a capacity terminal: fp32 halves the
pool's seats, so an arm that measured admission instead of numerics reports
NOT RUN rather than a verdict.

```
darkbloom benchmark --parity --model <id> [--assistant-model <drafter-id>]
```

Three exit statuses, and the distinction is the point:

| Status | Meaning |
|---|---|
| 0 | at least one criterion was evaluated and none failed (EXPECTED_SHORTFALL is evaluated, and does not fail the run) |
| 1 | an evaluated criterion FAILED |
| 2 | nothing was evaluated — every criterion UNAVAILABLE |

A criterion that cannot be evaluated reports UNAVAILABLE **with the missing
prerequisite**, never PASS by default; and an all-skipped run does not exit 0,
because "the gate is green" and "the gate never ran" must not look the same to
CI. Verdicts are keyed on the RESOLVED backend, so a `paged` arm that degraded
is compared as contiguous and the report says so rather than reporting parity
with itself.

**EXPECTED_SHORTFALL** exists because paged pays one `maxWindow` of extra
frozen replay over contiguous by construction, so a hybrid model can never
reach `paged >= contiguous` on prefix reuse. Calling that FAIL forever trains
readers to skip the criterion; calling it PASS lets someone conclude the
backends match. It gets its own verdict, does not make the process exit
non-zero on its own, and is named in the summary line so it cannot be missed
in the tail of a CI log. The shortfall is reported as a **percentage of the
baseline's saving**, because the cost scales as `maxWindow / matched`: measured
at 128 of 26,880 tokens (0.5%) on gpt-oss-20b's 128-token window, and 1,024 of
2,816 (36%) on gemma-4's 1,024-token window. Negligible on short-window models,
severe on long-window ones. The allowance is one `maxWindow`, **not** one
prefill chunk — they coincide on neither model measured (gemma-4: window 1024
vs chunk 512; gpt-oss: window 128 vs chunk 512), so "one chunk" would
mispredict both. A shortfall LARGER than one `maxWindow`, or any shortfall
from a backend whose prefix-reuse capability derived unsupported, is a plain
FAIL.

Those figures were measured against `libs/mlx-swift-lm` at `0b9cb42` and they
are expected to move: work narrowing the paged frozen-replay bound is in
flight, and the criterion derives its allowance live from
`candidate.replayBoundTokens - baseline.replayBoundTokens` rather than
hardcoding a window, so it re-scores itself without a harness change. If the
extra window goes away entirely the allowance becomes zero and the
EXPECTED_SHORTFALL verdict DISAPPEARS from the report rather than its
percentage shrinking — that, not a smaller number, is the signal that the gap
closed. Re-run the gate rather than trusting the numbers above once the
submodule pin moves.

Note it calls `EngineV2Factory.makeProductionBuild` directly and therefore
bypasses slot routing: every verdict is a statement about the BACKEND, not
about how production routes a slot to it.

### Compiled decode is removed

Incompatible with paged storage, and it had no B=8 rung — it fell back entirely
above B=4. Measured effect at B≤4 was roughly a wash (gpt-oss eager won by
~5%; gemma compiled won at B=2). `DARKBLOOM_CBV2_COMPILED` no longer exists.

### Memory: the activation reserve rises to a flat 5.5 GiB (3 → 5.5), both sides in lockstep

The reserve stays FLAT — every model, every attention posture, every batch —
but the number moves: **5.5 GiB**, up from 3. The 3 GiB floor was sized
against the B=4 measurement sweep; this release ships **decode batch 8**, and
the measured gemma-4 peak-over-resident-weights at B=8 is **5.05 GiB** (M4
Max 128 GB; B=4 was 3.40, gpt-oss 2.56 at B=8). An activation overshoot is
not a recoverable error — there is no MLX allocation-failure handler, so a
mid-request OOM **kills the daemon** — which at the old floor made B=8 a
daemon-kill lottery on near-cap boxes. 5.5 = measured 5.05 + ~0.45 slack.
`DARKBLOOM_ACTIVATION_RESERVE_GB` still raises it (never lowers it).

**Capacity impact, stated plainly: every box loses 2.5 GiB of KV budget.**
That shrinks per-slot token budgets (at gemma-4's ~400 kB/token cold rate,
about 6.7k fewer predicted post-load tokens per box) and makes small-box
co-residency strictly worse — a second model that barely fit beside the first
at 3 GiB may no longer load at 5.5. This is the deliberate, protective
direction: the memory was being spent by B=8 whether or not the ledger
admitted it; the old floor just let the daemon die instead of the load gate
saying no.

The coordinator mirror (`servabilityActivationFloorGB`, used by the
cold-servability predictor) moves in the **same commit**, so the predictor
keeps converging to the warm heartbeat report instead of re-learning the
desync lesson below.

**Retraction, kept for the record.** An earlier draft of these notes said the
reserve had become "a function of batch, query-block/span width, context and
heads". **That never happened on any box** — the parametric code landed with
zero call sites while the coordinator adopted it alone, charging cold models
a 65536 B/token surcharge no provider ever held and 429ing prompts the fleet
could serve. Both sides are flat again, the dead machinery is deleted, and
the flat-floor shape is the sanctioned one; this release moves the FLAT
number only.

**Known under-reserve, narrowed but not closed.** The raised floor now covers
the measured B=8 text-serving peak — that was its purpose. Two
configurations can still exceed it: **span-bearing vision chunks** take one
unblocked attention call (their `L` may snap over `prefillChunkSize` up to
the 2048-token step budget; pinned to batch 1, so at most one is live), and
`DARKBLOOM_CBV2_ATTN_QUERY_BLOCK=0` unblocks text prefill entirely — still
the one live configuration where any flat floor is provably wrong, and still
unsupported (see below; it also voids the G2 exactness gate). Raise
`DARKBLOOM_ACTIVATION_RESERVE_GB` if you serve long-context vision and see
pressure. And if an overshoot does kill the daemon repeatedly, the new
crash-loop backend guard bounds the blast radius on `.auto` boxes — see
above.

### Routing: the decode load factor is re-fitted

`effectiveTPSLoadFactor` moves 0.27 → 0.39, re-fitted against CBv2 measurements
(the old value came from a legacy engine on a dense 7B model and under-predicted
degradation by ~30% at B=8). This makes the concurrency cap slightly
**tighter**, and the warm-pool target and TTFT backlog estimates more accurate.

## `DARKBLOOM_CBV2_ATTN_QUERY_BLOCK`: two hazards, two different VALUES

Both consequences of this knob are recorded elsewhere in this document, in
sections written for different reasons, neither aware of the other. They
are named together here — but they are NOT the same hazard and they do not
attach to the same setting. Collapsing them into one blanket warning is
wrong in both directions.

**`= 0` — UNSUPPORTED.** Zero disables query sub-blocking entirely:
`shouldBlockQueries` is `queryBlockSize > 0 && L > queryBlockSize`
(`AttentionV1.swift:47-48`, env parsed at `:35-40`, default 128), so zero
restores the unblocked call. One switch covers both backends
(`PagedLayerCache.swift:705-707`). That is the one operator-reachable
configuration where the flat 3 GiB activation floor is provably wrong: the
unblocked score tensor is the term the floor was sized against, and the
loader admits against a number that no longer describes the work. Do not
run it in production.

**Non-default but non-zero (e.g. `128 → 8`) — supported, but it leaves
the measured fleet for exactness.** Sub-blocking stays ON and the score
tensor gets SMALLER, not larger, so the memory hazard above does not
apply. What changes is summation order, and that is enough to make
contiguous diverge from *contiguous* on 2 of 3 parity prompts with no
backend involved (`977a5893e`). This is exactly why G2 `token_exactness`
is a PASS-ONLY signal — the incumbent fails its own bar once the knob
moves — and the parity report cites the `8` case as a legitimate shipped
knob value when it explains that exclusion
(`BackendParityReport.swift:670-673`). A provider running a non-default
value is fine; it simply has no scored exactness signal, so do not read
its G2 row as evidence either way.

The two are independent: `0` breaks the reserve the loader admits against;
any move breaks the gate that would notice. Only `0` does both.

**Sibling knob, same class.** `DARKBLOOM_CBV2_PAGED_PTOK_TARGET` carries
the identical exactness hazard by the identical mechanism — it sized the
paged partition from batch composition, so a row's summation order moved
with its batchmates. It is DEFAULTED OFF for v0.8.0
(`PagedAttentionKernel.partitionTargetDefault = 0`) and pinned by a
regression arm that fails at `=128` and passes at `=8`
(`CBv2InvarianceTests.testPagedRowInvariantToBatchmateAttendedLength`).
Unlike the query-block knob it has no performance argument to weigh
against: measured directly on paged MTP verify at targets 0/32/128/512 on
gemma-4 geometry, no setting showed a throughput benefit. Treat both as
one class — exactness-affecting attention-shape knobs, default-only in
production, investigation-only otherwise.

## Compatibility

- **Wire format is unchanged.** The `lossy_snapshot` prefix-cache outcome is
  retained on the wire and still decoded by the coordinator, even though no
  code path can emit it any more — pre-0.8.0 providers remain in the fleet
  during rollout.
- Mixed-version integration gates were repaired for this release; they had been
  failing since v0.7.15 and that compatibility was therefore unverified.

### Shipped: `.auto` resolves PAGED

- [x] **The flip landed.** `.auto` resolves paged for every current and future
      model. This is the release's headline change, and it was made twice — the
      first attempt was reverted on evidence from `gemma-4-e2b-it-4bit`, which
      turned out not to describe production.

      **It is not primarily a performance change. It takes the fleet off the
      arm that returns wrong answers on prefix-cache hits.** Measured on the
      real slot path with the SSD tier, six arms, backend label confirmed on
      every one, cold-twin byte-identical throughout — cold vs adopted output
      for the same prompt:

      | model | paged | contiguous |
      |---|---|---|
      | `gemma-4-26B-A4B-it-qat-4bit` | **exact** | **diverges at byte 4** |
      | `gpt-oss-20b-MXFP4-Q8` | **exact** | **diverges** |
      | `gemma-4-e2b-it-4bit` | diverges | exact |

      The first two are the entire production catalog; `e2b` appears zero times
      in it. On contiguous, roughly **2.3% of flagship traffic** clears the
      26,624-token donation floor and could silently receive a shorter,
      truncated answer instead of an error. Paged does not.

      Throughput agrees rather than trading off: **1.27x** aggregate decode from
      B=4 to B=8 against contiguous's 1.07x, plus faster long prefill. B=1 is
      0.92x, which is the idle case — the coordinator's quality cap returns 8
      for gemma-4 on either backend's measured solo rate.

      **Rollback is one env var — per machine.** `DARKBLOOM_CBV2_PAGED_KV=0`
      lands on the kill-switch degrade, not a refusal; per slot:
      `engine_v2_kv_backend = "contiguous"`. There is no fleet push channel
      for env vars, so "fleet-wide" means a release or per-box operator
      action — and the crash-loop backend guard automates the per-box flip
      for the daemon-killing case.

- [x] **Batch raised to 8.** Right for both backends and shipped alongside the
      flip, because paged only overtakes above ~5 rows and the two are worth
      nothing apart. Upgrading providers with a serialized `= 4` are migrated
      once, announced in the startup log; a deliberately-set 4 is honoured.

### Accepted consequences, decided rather than inherited

- **gemma-4 greedy outputs change.** They are measurably more accurate against
  an fp32 reference — paged is 7–17x closer on gemma-4's full-attention layers
  — but they are **not identical**. Same prompt, different text. This was taken
  as a product decision, not read off a green gate. The same is already true
  across the shipped `DARKBLOOM_CBV2_ATTN_QUERY_BLOCK` knob, which makes
  contiguous diverge from *contiguous* on 2 of 3 test prompts.

- **The e2e exact-cache lane is expected red.** It runs `e2b`, the one
  checkpoint where paged adoption is the inexact arm. Kept pinned rather than
  silenced: it is a real signal about a model we do not serve, and it is the
  tracking item for e2b's paged frozen-bound path.

- **G3/G4 were not run.** They are 24-hour canary soaks and this migration has
  no canary fleet, so the soak *is* the canary. Every measurable gate (G0a,
  G0b, G1, G2, G5) passes on real weights. Watch the first fleet day with
  `DARKBLOOM_CBV2_PAGED_KV=0` ready.
