# Gemma expert placement candidates

Source-derived design note, 2026-09-15. No expert-parallel implementation or throughput measurement is established by this note. The verified registered Gemma4 text artifact has 128 experts, top8 routing, hidden size2816 and expert intermediate width704. Actual activation dtype must be established by the native probe before buffer admission; the byte examples below assume BF16.

A whole-expert placement should route by destination Mac, not create a network copy for each selected expert. For a token whose selected experts include multiple experts on the other Mac, send one hidden vector plus the selected remote expert IDs and routing weights. Execute all selected local experts there, sum their weighted contributions locally in the prescribed arithmetic order, and return one partial hidden vector. Any change in reduction order must pass the model's numerical policy; equivalent real arithmetic does not guarantee identical floating-point output. Routing IDs/weights/activations/results all belong inside authenticated ciphertext.

With two Macs and attention owned by one Mac, the residual-vector component is bounded by one outbound and one return hidden vector per routed token per expert layer. It is not necessarily eight outbound copies because top8 experts were selected. If all experts are local, no remote expert payload is needed for that token; zero-work rank participation and synchronization still need explicit protocol behavior. Destination compaction and token-index maps cost memory and compute and must be measured. The shared FFN and attention are separate placement choices, and their work cannot be omitted from the planner.

At C512/H2816/BF16, a hidden block is2,883,584bytes (2.75MiB). The straightforward outbound/return bound is5,767,168bytes per block per distributed expert layer, plus encrypted routing/control/framing. This is a logical payload estimate, not a measured wire rate, process peak, or count for the current layer-only implementation. Multiplying across the actual request DAG must account for which layers cross machines, reuse of already-replicated activations, chunk boundaries, and idle/overlap intervals. A pipeline has fewer cross-machine boundaries; expert parallelism may offer better within-layer balance. Neither is a universal winner.

Compare at least four qualified candidates: whole-layer stages; whole-expert banks with destination-compacted dispatch; expert intermediate-width splitting; and a hybrid. The existing experimental width partition320/384 conserves704 and keeps64-element quantization groups aligned, but changes kernel shapes. Whole experts retain full local intermediate width and avoid that shape split, while routing skew can imbalance work. A hot-expert replica costs resident memory and should be selected from measured expert occupancy without persisting prompts or inference payloads.

The planner needs per-layer expert-token occupancy and grouped-kernel latency at the actual prompt/batch shapes, shared-work latency, destination dispatch and combine costs, encrypted transfer/fence costs, and per-rank measured peaks. Use token counts and timings, not model content, as telemetry. Reserve all expert weights required by the selected plan even though only8 experts activate for one token. Different model families supply geometry, routing semantics, shared-expert handling and supported quantization/kernel partitions through adapters; do not reuse these Gemma dimensions as generic constants.

Current implementation status: Gemma metadata and layer-stage/native-value checks pass; the current map puts each entire layer and all its experts on one rank. Shared windowed state, actual Gemma generation, expert dispatch, secure routing and measured selection remain required work. The layer-pipeline Qwen result provides a control to beat, not proof of this proposed expert layout.
