### Releases carry their cluster runtime facts

- Every release lane (dev branch, staging, prod) now computes the cluster runtime facts of its final signed app with that app's own CLI and worker: the digests of the cluster worker, placement tool, Metal library and paged-attention source, and for each model the build qualifies on a cluster and the environment's catalog has, the digests of its capability. The job summary and a run artifact show them in every release.
- GLM-5.3-Flash and Qwen3.8-27B are declared for public cluster traffic in tensor parallel (owner decision, 2026-10-31): their entries carry parity qualifications (two Apple M5 Ultras, both prefill schedules, sampling and tools, and images and video as the environment's catalog lists them), from which a coordinator derives their public qualifications. Every other model's clusters serve their owner only. The setup says a declared model is qualified for public traffic in tensor parallel.
- The release registration carries the facts as `cluster_runtime` only when that environment's repository variable (`DEV_CLUSTER_RUNTIME_ENABLED`, `STAGING_CLUSTER_RUNTIME_ENABLED`, `PROD_CLUSTER_RUNTIME_ENABLED`) is `true`; a coordinator that accepts the block then approves the build's two-Mac clusters automatically. Unset, the registration is unchanged and a failure to compute the facts only warns.
- `darkbloom cluster runtime-facts` (hidden) prints schema `darkbloom_cluster_runtime_v2`: the same digests as before plus each model's `parity_qualifications`.
