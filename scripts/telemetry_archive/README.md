# Copy-only telemetry snapshots

Capture complete bounded snapshots from a physical PostgreSQL read replica,
encode them as compressed Parquet, upload immutable objects to a private GCS
Standard bucket, and verify decoded contents and BigQuery query results.
This tool does not delete data, change retention, run migrations, create cloud
resources, or install a recurring job. Receipts explicitly say
`copy_only=true` and `retention_eligible=false`.

The five allowed tables are `request_profiles`, `fleet_snapshots`,
`request_rejections`, `inference_routes`, and `request_outcomes`. Financial and account tables
are rejected. Route snapshots describe one database snapshot; they do not
claim to capture future outcome updates or every historical row version.

## Run

Use Python 3.12 and uv (CI uses 0.10.9):

```sh
cd scripts/telemetry_archive
uv sync --locked
uv run telemetry-archive --help
```

Provide `ARCHIVE_DATABASE_URL` through the environment, using a SELECT-only
role and a connection to the physical replica. The CLI has no primary bypass.
Every source transaction is repeatable-read and read-only with a 15-second
statement timeout, 1-second lock timeout, and 30-second idle timeout.
Use a Cloud SQL Auth Proxy or connector for connector-enforced instances.

```sh
uv run telemetry-archive capture \
  --table request_profiles \
  --start 2026-09-07T20:00:00Z --end 2026-09-07T20:01:00Z \
  --directory artifacts/profile-pilot

uv run telemetry-archive verify-local --directory artifacts/profile-pilot

uv run telemetry-archive upload \
  --directory artifacts/profile-pilot \
  --project darkbloom-mainnet --bucket YOUR_ARCHIVE_BUCKET

# Pass the receipt_uri returned by upload.
uv run telemetry-archive verify-remote \
  --project darkbloom-mainnet --receipt gs://YOUR_ARCHIVE_BUCKET/receipts/v1/ARTIFACT_ID.json \
  --bigquery --maximum-bytes-billed 1073741824
```

Cloud clients use Application Default Credentials. A local pilot can instead
supply a short-lived token through `ARCHIVE_GOOGLE_ACCESS_TOKEN`; never commit
tokens, database URLs, or production snapshot files. The container can use its
service identity. No secrets are accepted as command-line arguments.

The bucket must already exist, be private with enforced public access
prevention and uniform bucket access, use STANDARD in the requested region
(default us-east4), and have no lifecycle rules. Creation and IAM changes are
separate operations. An existing logs bucket with a deletion lifecycle is
deliberately rejected.

## What is verified

- COUNT and export use one source snapshot; insert/commit order and sparse IDs
  are never interpreted as completeness beyond that snapshot.
- Source records remain complete in `row_json`, generated by PostgreSQL's
  `row_to_json`, alongside their original PostgreSQL type catalog. Useful
  fields have typed Parquet projections; new columns remain in complete JSON.
- Local readback checks schema, source count, ordered content SHA-256,
  individual row SHA-256, every projected value, time bounds, and file checksum.
- GCS writes use create-only preconditions, then download the exact generation
  and verify SHA-256. Same-artifact upload retries reuse identical objects;
  inconsistent existing objects fail without overwrite or deletion.
- The data object is verified before its file manifest is written. The remote
  receipt is written last. Partial runs have no successful receipt.
- Remote verification re-downloads and decodes the objects. BigQuery uses a
  temporary external table over the manifest-verified data URI and checks row count, distinct IDs,
  per-row payload hashes, time bounds, and ID/time extrema. No persistent
  BigQuery dataset/table is created; the query has a hard bytes-billed limit.

One snapshot is at most one hour within a UTC date. Defaults: 1,000 rows/page,
250,000 rows, 512 MiB raw JSON, and 120 seconds. Upper resource limits are
validated. Exceeding a bound or any query failure prevents receipt creation;
split the interval and rerun into a new directory. An existing local capture
directory is never overwritten. An interrupted local file is not a snapshot.

Different captures of the same window can contain late commits or updates and
receive different receipts. Query one receipt at a time. Do not wildcard-union
receipts and count overlapping snapshots as distinct events. This first
version has no automatic ongoing high-water mark.

## Resumable finite backfills

`prepare-plan` freezes explicit ranges for the five allowed telemetry tables.
`upload-plan` publishes its content-addressed plan in the existing bucket.
`run-backfill` processes non-overlapping hourly windows, splitting oversized or
timed-out captures down to at most one minute. A window that still fails stops
the run. Every completed leaf is independently uploaded and verified through
BigQuery before a create-only checkpoint is recorded.

```sh
uv run telemetry-archive prepare-plan --ranges ranges.json --output plan.json
uv run telemetry-archive upload-plan --file plan.json \
  --project darkbloom-mainnet --bucket darkbloom-mainnet-telemetry-archive
uv run telemetry-archive run-backfill --plan-id PLAN_ID \
  --project darkbloom-mainnet --bucket darkbloom-mainnet-telemetry-archive \
  --max-run-seconds 21000
```

`ranges.json` is an array of `{ "table": "request_profiles", "start":
"2026-09-03T21:00:00Z", "end": "2026-09-09T00:48:00Z" }` objects. Use actual
indexed source bounds. Each table may appear once, and each range is at most
365 days. Freeze the end explicitly; this is a finite historical copy.

The runner checks replica replay age before every new capture and exits with
code 75 when it exceeds 30 seconds or the execution budget is exhausted.
Runtime budgets are checked between windows; the hosting platform must also
set its hard task timeout. No automatic service retry or schedule is created.
Rerun the same plan ID to resume. Saved data/manifest generations are checked
before skipping completed work. Persistent split decisions prevent overlapping
parent/child snapshots from entering the same completed coverage.

Only after every planned window is verified does the runner write
`backfills/v1/PLAN_ID/summary.json` and per-table `catalogs/TABLE.json` files.
The catalogs name the exact non-overlapping data files and generations; earlier
pilots and alternative snapshots are excluded. No source retention is involved.

For a colocated Cloud Run Job, use its managed Cloud SQL socket and mount the
existing read-replica access JSON as a secret. Set `ARCHIVE_ACCESS_FILE` to the
mounted path and `ARCHIVE_EXPECTED_INSTANCE` to the exact replica connection
name. The adapter verifies that the credential names the expected instance,
and the source still enforces physical-replica and read-only checks. See the
[backfill launch runbook](../../docs/operations/telemetry-backfill.md) for the
separate infrastructure approval and resource scope.

## Test

```sh
uv run ruff check src tests
uv run ruff format --check src tests
uv run pytest -q
```

PostgreSQL integration tests run only when `TEST_ARCHIVE_DATABASE_URL` points
to a disposable local database named `archive_test`. They create test tables
there and refuse other hosts/database names. CI provides it. Tests cover
lossless JSON/numeric/Unicode restoration, new fields, consistent snapshots,
late commits, source failures, corrupt files, partial uploads, upload retries,
unsafe buckets, generation replacement, and BigQuery disagreement.

`uv.lock` pins local/CI resolution. The container uses `requirements.lock`,
generated with `uv export --frozen --no-dev --no-emit-project --no-header --format
requirements-txt --output-file requirements.lock`; keep them aligned.

See [the operator runbook](../../docs/operations/telemetry-archive.md).
