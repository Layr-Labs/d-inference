### The provider says why it couldn't read Secure Boot, and reads it again

- When `system_profiler` can't report the Secure Boot setting, the Darkbloom service reads it again for up to a minute before it starts serving. On a Mac that serves alone, while the setting stays unread, the service reads it once more before each connection to Darkbloom. The service no longer reports `unknown` from one failed read; `darkbloom doctor` and `darkbloom status` still read it once.
- When it stays unread, the registration says why (`secure_boot_read_failure`: `timed_out`, `launch_failed`, `exit_status`, `output_too_large`, `output_unreadable`, `not_json`, `no_report`, `no_value` or `unrecognized_value`) and after how many reads (`secure_boot_read_attempts`). The provider's log records each failed read, and `darkbloom doctor` and `darkbloom status` name the reason.
- A `Reduced Security` or `Permissive Security` setting found by a later read at startup holds before anything loads, like one found by the first read. One found before a connection keeps this Mac from registering with Darkbloom until the service restarts; models already loaded and this Mac's own local API stay up, as with Only me.
