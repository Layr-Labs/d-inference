# Trust bootstrap source review

The existing private release catalog can verify and approve ad-hoc artifact bytes, but that operation alone cannot satisfy the current verified-pair trust gate. A qualified current member needs genuine code identity and device proof in addition to the approved hashes. No gate change is proposed.

## Signing conclusion

`coordinator/api/release_handlers.go:73` authenticates the scoped release publisher, downloads the configured artifact, verifies archive/binary hashes and synchronizes release/runtime policy. `verifyReleaseArtifact` at line 345 does not inspect an Apple signature. Therefore describing release registration itself as a Developer ID check would be incorrect.

The full gate at `coordinator/registry/verified_pair_membership.go:22` separately requires hardware trust, MDA, SE-key binding, CodeAttested, FreshCodeAttested, metallib verification, current release/application evidence and fresh challenges/heartbeat. `coordinator/api/provider_codeattest.go` earns code proof through real APNs, or a genuinely earned eligible cached APNs proof followed by a fresh encrypted challenge to the current process key. A public key, old trust status, private hash allowlist or disabled global APNs enforcement deadline does not satisfy these predicates.

The supported release workflow in `.github/workflows/release-swift.yml` uses Developer ID Application for team SLDQ2GJ6TL, an embedded profile granting the exact keychain group and production APNs entitlement, and checks that get-task-allow is absent. The shared signature requirement in `DarkbloomCodeSignature.swift` is Apple anchor + team SLDQ2GJ6TL + bundle identifier io.darkbloom.provider; it does not literally require a particular Developer ID certificate class. No claim is made here that an alternative signing class has been qualified.

The normal member startup does not call `SignedReleaseIdentity.verifyCurrent` (the observed caller is a benchmark). `ProviderLoop.createAttestationSigner` first loads the entitled persistent SE key and falls back to an ephemeral key on failure. Thus an ad-hoc process can reach an unqualified registration instead of immediately refusing startup; that is not proof that it can pass the pair gate. The intended same-identity route uses `SLDQ2GJ6TL.io.darkbloom.provider`, the genuine APNs-capable app process and its existing persistent signer. Do not rotate the key or substitute a signed helper to make this audit appear successful. The key's load-or-create/repair method itself may mutate key identity and was not executed.

Root reports zero local signing identities. This does not imply the private signing key must be installed locally: an already-authorized team/CI signing path can supply the exact candidate app and profile. The new signed bytes and packaged app must then be measured and bound to the private release/driver configuration; the current unsigned/ad-hoc test binary's hash cannot be reused as its identity.

## Minimum missing access and configuration

1. A genuine signing/provisioning route for the exact new member CLI: existing authorized team/CI or supplied exact signed app, with the above keychain and production APNs capabilities. Existing older signed software is not evidence that this new executable is approved.
2. Genuine code-attestation service: APNS_KEY_ID, APNS_TEAM_ID, the authorized .p8 through APNS_AUTH_KEY_P8_PATH or APNS_AUTH_KEY_P8_B64, and matching topic (default io.darkbloom.provider). A still-valid genuine cached proof plus the existing live resume protocol can avoid a new push, but no such usable private-store proof has been demonstrated. Both actual member processes also need their genuine APNs token/active console-session delivery path; the existing readiness source documents that headless registration may not obtain one.
3. Authorized access to the actual MDM enrollment/service and current proof records for the two exact Macs: EIGENINFERENCE_MDM_URL and valid MDM API authorization, plus correct callback routing for the existing verification scheduler if fresh verification is needed. A genuine cached Apple MDA chain is only reusable after current hardware binding, Apple-root/expiry verification and FreshnessCode equality with SHA256 of the exact registered public-key string. The public attestation feed's se_public_key is useful for identity matching but contains no MDA chain and cannot supply that proof. Enrollment alone is insufficient.
4. A separate private coordinator store and scoped release-publishing configuration: EIGENINFERENCE_RELEASE_KEY, the configured trusted artifact origin and the real release/runtime metadata. PostgreSQL and gcloud are not necessary to start this isolated test: the existing explicit EIGENINFERENCE_ALLOW_MEMORY_STORE=true path is available. A fresh memory store contains no old genuine proofs; these must still be earned through normal verification. A configured loopback HTTP artifact origin is already supported. No production catalog/database mutation is needed for this private plan.

The bootstrap document additionally asks for real account/auth linkage. That is sensible operator/account binding, but it is not a mandatory predicate in the inspected private hardware selector or verified-pair gate: registration resolves a supplied provider token when valid and permits an absent token; the hardware selector selects exact serial + SE-key hash. Do not report missing Privy/gcloud/account credentials as the cryptographic blocker for this bounded pair path. If account attribution is required operationally, use the real provider-token workflow rather than copying another environment's token.

## Scope and limits

This was a source review of the frozen 332bb startup plan, relevant current MAIN security paths and the private selector. Root's observations (no local MDM/DB/APNs configuration, no gcloud, zero valid code-signing identities, public feed key without chain) are explicitly reported observations, not new probes by this reviewer. Existing TLS correctness and native cleanup results do not establish these missing trust predicates. No compiler, keychain operation, remote request, enrollment command, production mutation or trust-flag write was performed. Frozen sources remain unchanged. The exact TLS/member/native approval and capacity gates remain closed until their real inputs pass.
