Coalescing is technically feasible without converting values, but the current16MiB generic P2P limit prevents a literal single transfer for a P4096 snapshot. The smallest useful candidate would be one explicitly owned logical payload, sent in one bounded transfer at P128 or two at P4096. It should wait for the newly staged conditioning/reseed timers: it trades fewer synchronizations and checks for packing/copying work, so no speedup is established by this source audit.

Current Snapshot.send makes seven completed tensor transfers: hidden, two heads of fullK, two heads of fullV, slidingK and slidingV. Receive makes those same seven allocations and two full-head concatenations, retaining nine roots through fences and worker installation. Each generic transfer retains the original CPU+GPU C-status fences. Within Snapshot.receive alone this is14 stream synchronizations from receives plus4 from the two concatenations plus2 from its final capture fence. The target sends have14 stream synchronizations. Worker/branch and protocol fences are additional and must remain. Packing can reduce the number of actual operations; it is not authority to omit a remaining operation's checks or completion fences.

Pinned MLX APIs and exact semantics:

- MLXArray+Ops.swift exposes public view(dtype:stream:). Its contract guarantees unchanged binary representation, adjusts the final dimension when element widths differ, and explicitly does not guarantee shared storage. This is the correct reinterpretation API; asType is a numeric conversion and must not replace it.
- ops.cpp view validates divisibility when viewing bytes as larger elements. CPU and GPU View backends share backing when element widths match, when narrowing with last-axis stride1, or when input is row-contiguous. Other cases allocate and copy. CPU reshape and common prepare_reshape share an already row-contiguous input; a general reshape may allocate. Therefore views/flattening need either proven layout predicates or separately charged potential copies.
- concatenate computes a common dtype and casts inputs to it before copying. Concatenating FP16/FP32 hidden directly with BF16 KV is unacceptable. Concatenating five verified BF16 arrays introduces no mixed-type promotion. A uint8 carrier made from binary views also avoids promotion for every supported hidden dtype.
- Generic Send ensures row-contiguous storage, possibly allocating a temporary; its returned handle aliases the input. Recv creates a new allocation. The existing Swift shim checks the completed receive's unique, row-contiguous, zero-offset, exact logical-size storage before returning it. Those checks must run before creating component aliases, not against each later view.
- evaluatedBufferInfo never evaluates or waits and does not grant ownership credit. allocationFootprintUpperBound bounds one actual allocator allocation; separate graph inputs/copies need separate bounds. asData(.copy) creates independent host storage and implicitly calls eval; no-copy Data is valid only while its MLXArray remains retained. Neither is a free packing or encrypted-transport path.

The BF16 fast path can flatten and concatenate the five logical components in canonical order hidden/fullK/fullV/slidingK/slidingV, then send the packed BF16 vector. The receiver derives all offsets from the admitted frontier and exact hidden dtype, slices one completed backing and reshapes the five views. If hidden is FP16 or FP32, a byte-preserving packed fallback is available: view each original component as uint8, flatten, concatenate uint8, then slice byte ranges and view each result back to its original dtype. Every byte offset and length must be checked for the restored element width; current shapes make them multiples of4, but the codec should validate this explicitly. A lower-risk initial alternative is to retain the existing seven-tensor path for those mixed dtypes until native byte-roundtrip tests pass. Actual hidden dtype must select the path; BF16 weights or budget maxima do not prove hidden dtype.

This is only codec pseudocode, not runtime implementation or an approved wire change. Both ranks must derive a versioned packing mode, component order, exact offsets/shapes/dtypes, total bytes and chunk schedule from the same admitted request/branch snapshot identity. Their existing seed/seeded exchange must bind the chosen layout in its scope. A remote header cannot enlarge a buffer or choose an unexpected fallback. Existing frontier, seed, ordinal and target-authoritative acceptance remain exact.

Allocation/lifetime obligations are the main implementation boundary. Let A(n) be the actual allocator bound. A conservative sender must charge each possible compact/reshape allocation separately, the packed output A(L), and any possible native compact-send temporary. Existing seven per-head pack terms cannot silently cover two larger full-tensor reshapes: allocator rounding is per allocation. Initially retaining old reserves and adding new named terms is safe; discounts require an explicit exact proof. An admitted packed row-contiguous output can remove the need for a second Send compact copy, but that layout/lifetime must be checked rather than assumed.

For a one-transfer receiver the payload allocation is A(L), with five component views that retain the complete backing. For two transfers, retain both chunk allocations plus the assembled A(L) until the actual assembly fence and installation finish. Any dtype-view/reshape copy adds its own A(componentBytes) unless actual contiguity proves aliasing. All these terms must be checked against the existing three-snapshot allowance using actual A values; equal logical totals do not establish equal allocation bounds. A new layout-specific named plan may fit the reserve, but the current nine-root plan is not that proof. No floor, reserve or host allowance is reduced by this audit.

The target's existing pendingCapture is insufficient to prove a newly allocated packed payload's failure lifetime: the original target or a bounded transfer-staging field must retain that pack before its first evaluation/send, and retain it through seeded ACK or actual original-owner failed retirement. On the assistant, the same service owns chunk/assembly/view staging before any evaluation; a failed fence retains all roots. Successful installation must leave the worker's capture/branch holding the shared backing before service staging clears. No ACK can imply branch/root retirement while a packed backing is still intentionally retained.

Transport's separate delta prototype keeps the initial seven transfers unchanged and assumes four separately allocated old KV mirror roots plus five delta receives/four assemblies. A packed view would retain the entire L-byte backing, including hidden, when any KV view survives. That is explicitly outside its13-root proof. Combining the two candidates requires a new backing/liveness plan; do not subtract an old hidden allocation merely because its named view was dropped.

The same canonical byte layout can be input to authenticated-record transport, but packing is not encryption or a new transport authority. The existing record adapter uses expected array shape/dtype and metadata digest, authenticates before materializing native output, and uses independent directional keys/sequences. The layout version, request/branch/snapshot and chunk index/count must join that authenticated expectation; there is no raw fallback after authentication failure. Its framing adds40B and its generic ceiling is also16MiB, so each exact record payload is at most16MiB-40B, potentially much smaller under a selected runtime policy. Host plaintext/ciphertext/record copies, native frame buffers and crypto workspace remain separate charges. Main record sources are pinned as context only; this audit does not qualify Gemma encryption or the backend's confidentiality behavior.
