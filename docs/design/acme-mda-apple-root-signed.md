# Apple-Root-Signed ACME (device-attest-01) with MicroMDM — Design

**Status:** implemented. The coordinator verifies step-ca-issued ACME client
certificates forwarded by the TLS terminator (`coordinator/api/acme_verify.go`),
and generates the MDM + ACME enrollment profiles (`coordinator/api/enroll.go`).
This doc explains the design space we explored, the macOS platform constraints
that shaped it, the decision we landed on, and the residual analysis of
multi-node (RDMA) inference.

> Historical note: this document originated as an exported design conversation.
> It has been rewritten as a proper spec; the conclusions are unchanged.

---

## 1. Goal

Bind a provider Mac's identity to **Apple's hardware root of trust** so the
coordinator can verify, cryptographically and without trusting anything the
provider self-reports, that:

1. the machine is **genuine Apple Silicon hardware** (not a VM or emulator),
2. the device is **enrolled in our MDM** (MicroMDM), and
3. the device's security posture (SIP status, Secure Boot policy) is what the
   device — not the provider's software — says it is.

The mechanism is **ACME `device-attest-01`** (Managed Device Attestation, MDA):
an MDM-delivered `com.apple.security.acme` profile makes the device generate a
hardware-bound key in the Secure Enclave and obtain a certificate from our CA
(Smallstep `step-ca`), where issuance is gated on an **attestation generated by
the SEP and signed under the Apple Enterprise Attestation Root CA**. Apple will
not produce this attestation for non-genuine hardware.

## 2. Architecture

Three components, with clean separation of duties:

| Component | Role |
|---|---|
| **MicroMDM** | Delivery only. Pushes the `.mobileconfig` containing the `com.apple.security.acme` payload. MicroMDM needs no native ACME support — profiles are just payload containers. |
| **step-ca** | The ACME server. A provisioner with `--challenge device-attest-01 --attestation-format apple` verifies the Apple-signed attestation before issuing the client cert. |
| **Coordinator** | Consumes the result. nginx (or the TLS terminator in front of the coordinator) requests/verifies the client cert and forwards it via headers; `acme_verify.go` re-verifies it against the step-ca root and extracts the device serial. |

### ACME payload (key fields)

```xml
KeyType          = ECSECPrimeRandom
KeySize          = 384            <!-- SE P-384 -->
HardwareBound    = true           <!-- key generated in / bound to the SEP -->
Attest           = true           <!-- request Apple MDA attestation -->
DirectoryURL     = https://<step-ca>/acme/acme-da/directory
ClientIdentifier = <device serial / UDID>
```

### The trust chain

```text
Apple Enterprise Attestation Root CA (P-384)
  └─ Apple Enterprise Attestation Sub CA
       └─ Device attestation cert (SE-generated; OIDs carry serial,
          SIP status 1.2.840.113635.100.8.13.1,
          Secure Boot 1.2.840.113635.100.8.13.2, freshness nonce)
            └─ step-ca verifies attestation → issues ACME client cert
                 └─ device presents client cert (mTLS) → coordinator
```

Crucially, SIP and Secure Boot state ride **inside the Apple-signed
attestation** (macOS 14+ on Apple Silicon), so a compromised OS cannot lie
about them — this is what lets the coordinator's `hardware` trust level mean
something against a root-level attacker.

### Coordinator verification (`acme_verify.go`)

The TLS terminator does the mTLS handshake and forwards:

- `X-Ssl-Client-Verify` — must be `SUCCESS`,
- `X-Ssl-Client-Cert` — URL-encoded PEM of the client cert,
- `X-Ssl-Client-Dn` — subject DN.

`extractAndVerifyClientCert` then independently re-verifies the chain against
the pinned **step-ca root** (`stepCARootCert`), extracts the device serial from
the CN, and the P-256/P-384 public key. The result feeds the provider's trust
level: a valid ACME-MDA client cert is a precondition for `hardware` trust
(alongside the MDM SecurityInfo cross-check — see
[apns-code-attestation-design.md](apns-code-attestation-design.md) for the full
attestation layer stack).

## 3. The macOS keychain constraint (why the design is shaped this way)

The single most important platform fact: **MDM-provisioned hardware-bound
identities are inaccessible to third-party processes.**

macOS has two keychain implementations:

- the legacy **file-based keychain** — supports `AllowAllAppsAccess`, but
  **cannot** hold hardware-bound keys;
- the **data protection keychain** — holds hardware-bound (SE) keys, but
  identities installed by device management land in a keychain access group
  restricted to Apple system services (built-in VPN/IKEv2, Wi-Fi EAP-TLS,
  Kerberos, Safari mTLS). `HardwareBound: true` forces this keychain.

So our provider process — no matter how privileged — **cannot** call
`SecItemCopyMatching` against the ACME SE P-384 key, and cannot use it for
application-level signing or prompt decryption. The key is usable only by the
OS itself.

### Options we evaluated for app-level use of the cert

| Option | Mechanism | Verdict |
|---|---|---|
| **A. Drop `HardwareBound`** | `HardwareBound: false` + `AllowAllAppsAccess: true` → file keychain, app-accessible | Rejected: loses the SE non-extractability guarantee, which is the point. |
| **B. Derived certificate** | Keep SE P-384 MDA cert as the root of trust; a second step-ca provisioner with a webhook (checks MicroMDM `DeviceInformation` attestation status) issues a short-lived app-accessible cert into the file keychain | Viable, no Apple gatekeeping; adds a webhook service + second profile. The derived key is not SE-bound but issuance is hardware-gated and lifetime is short (hours). |
| **C. Per-app VPN (built-in IKEv2)** | `com.apple.vpn.managed` (IKEv2, cert auth, `PayloadCertificateUUID` → ACME payload) + `applayer` + `appmapping` payloads. The built-in IKEv2 client *can* read the data protection keychain; app traffic is tunneled with SE-P-384-authenticated IPsec | Viable with no entitlement; cost is running an IKEv2 gateway (e.g. strongSwan trusting the step-ca root). |
| **D. Network/System Extension** | Custom `NEAppProxyProvider` with the `com.apple.managed.vpn.shared` keychain group entitlement | Rejected: the entitlement is Apple-gated via DTS with unpredictable (weeks-to-months) turnaround. |

### Decision

We do **not** need the ACME key for application crypto at all. The crypto is
split across two layers, each key doing the work it is actually capable of:

- **SE P-384 (ACME/MDA)** — *device identity and posture*. Used for mTLS to
  the coordinator's enrollment/verification endpoints and as the
  hardware-rooted gate for `hardware` trust. Never used by app code.
- **SE P-256 (CryptoKit `SecureEnclave.P256`)** — *application identity*. A
  provider-generated SE key signs attestation blobs (and is bound to the
  device by serial-number match against the MDA chain). See the attestation
  blob spec in [../ARCHITECTURE.md](../ARCHITECTURE.md#security--attestation).
- **X25519 (NaCl box)** — *E2E request encryption* (provider-held key,
  published at registration). The consumer verification flow at
  `GET /v1/providers/attestation` links it to the attestation blob.

The binding that makes this one chain: the MDA cert (Apple-signed) carries the
device **serial number**; the attestation blob (SE-P-256-signed) carries the
same serial plus the P-256 and X25519 public keys. A verifier walks: Apple root
→ device cert → serial match → blob → response-signing / encryption keys.

## 4. Residual analysis: multi-node inference and RDMA

A recurring question is whether the security model survives multi-Mac clusters
(e.g. exo-style split inference over Thunderbolt RDMA). **It does not, by
design — single-node is the supported trust boundary.**

- Enabling RDMA (`rdma_ctl enable` from recoveryOS) is a **separate NVRAM
  setting from SIP** — SIP can remain on, so naive attestation doesn't notice.
- RDMA is hardware-level remote memory access. It bypasses every software
  protection in the hardened-process model: `PT_DENY_ATTACH` (no ptrace
  involved), Hardened Runtime (no Mach APIs), SIP (no kernel bypass needed).
  A second machine on the fabric can read the inference process's unified
  memory — plaintext prompts included — over a cable.
- Encrypting activations in transit does not help: the receiving node must
  decrypt to compute, so plaintext exists in the (adversary-owned) receiver's
  memory; and activations are derived from prompts (early-layer activations
  are close to embedding space and partially invertible).
- The mitigations that would work do not exist on Apple Silicon today:
  hardware memory encryption for third-party code (à la SEV), GPU-capable
  enclaves, or FHE at interactive speeds (10⁴–10⁶× overhead).

**Policy:** multi-node RDMA inference is out of scope. If it is ever added, an
RDMA cluster must be treated as a **single co-attested trust unit** (every node
passes all attestation layers; adversary model restricted to parties outside
the cluster), or providers with RDMA enabled must be disqualified outright by
adding RDMA status to the attestation checks. The economics independently favor
single-node: the MoE models that make sense on Apple Silicon fit one box, and
dense 70B+ models are cheaper on cloud GPUs anyway.

## 5. Where it lives

- `coordinator/api/acme_verify.go` — client cert extraction + step-ca root
  verification (`ACMEVerificationResult`: serial, issuer, public key).
- `coordinator/api/enroll.go` — MDM + ACME enrollment profile generation
  (no auth required: enrollment is open; trust is earned via attestation).
- `coordinator/mdm/` — MicroMDM client + webhook handling (SecurityInfo
  cross-check for `hardware` trust).
- `scripts/deploy-acme.sh` — nginx + step-ca deployment helper.
- Trust-level consumption: `coordinator/registry/` (routing multipliers),
  `coordinator/attestation/` (blob verification).
