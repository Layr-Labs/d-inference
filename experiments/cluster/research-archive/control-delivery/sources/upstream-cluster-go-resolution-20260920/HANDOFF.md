Capability reconciliation retains the upstream lock contract. It acquires `r.mu.RLock`, captures the current provider and its exact pair state, acquires `provider.mu`, and evaluates the current App Attest lease while both locks are held. On exit it computes the original pair-revocation predicate while holding `provider.mu`, unlocks the provider, then unlocks the registry read lock. Only then may `invalidateVerifiedPairState` acquire the registry write lock. Capability notification follows invalidation outside both locks. A missing provider releases the read lock once before returning. The named `reconcileError` return is retained, so a failed claim-validation return also revokes the captured grant. Exact-state invalidation cannot clear a replacement grant with the same textual provider ID.

This merge deliberately preserves the current stricter native-pair identity contract. `verifiedPairMemberLocked`, cleanup release, transcript fields and native control verification still use verified MDA/SE identity, APNs/application evidence, runtime/metallib approval and original connection/generation. Upstream’s separate App Attest serving lease must not be represented by fabricating these legacy flags. The later identity-kind change needs explicit account/machine/credential/endpoint and signing-key bindings, generation/expiry checks, device exclusion, revocation/reconnect, and original-owner cleanup semantics. It must reach every pair admission/revalidation/release reader and all mirrored transcript/control records. This proposal neither enables that path nor treats an App Attest process endpoint as an SE signing key.

The source review traced the existing pair invalidation helpers, current strict member/release gates and upstream `providerHasAppAttestAuthorizationLocked`.
