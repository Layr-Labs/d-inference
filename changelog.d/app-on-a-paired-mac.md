### The app on a paired Mac offers Start serving, and its lines say what happened

- On a Mac in a two-Mac pair, the app's Autopilot was a dead end. Onboarding's **Start serving with Autopilot** first downloaded a model, then showed three lines meant for the command line, and **Retry** showed them again. Autopilot chooses the models of one Mac, so on a paired Mac it is now refused before anything downloads, in words the app shows: "This Mac serves in a pair; Autopilot isn't available for pairs yet. Use Start serving." The Autopilot page's model refresh is refused the same way.
- The app now offers **Start serving** on a paired Mac, which starts the pair. Its onboarding says "This Mac serves in a pair. Start serving starts the pair with <model>.", and it starts the pair without naming a model or a local API of its own. When the pair has no model yet, it says so in one line: "No model was chosen for the pair yet: run `darkbloom start` in a terminal to choose one." The Mac tells the app it is in a pair, so even an app from before this offers the plain start there.
- After the app's Start on a paired Mac, its last lines say what happened. When the app named another model, the pair "serves" its own model, or "was asked to start" with it and "isn't serving" when it doesn't serve yet. Before, it said "serves in a pair: started the pair" in both cases, and also for a pair that was already running. When the app asked for a local API that the pair doesn't give this Mac, it now says "No local API was added on this Mac", with where to change how the pair serves.
- When a pair's other Mac isn't answering and this Mac's part was given up after 15 minutes, a start's `Next:` line and `cluster status --json`'s `next` now also name `darkbloom start --solo` to serve this Mac alone.
