### Master push publishes dev and staging provider releases

- A push to `master` now publishes a staging provider release in parallel with the dev release (DBLM-771: staging tracks main), gated by the `STAGING_ENABLED` repository variable. Staging is a normal Developer-ID dev-family release signed with the same certificate as dev and prod, versioned `X.Y.Z-staging.N` by the workflow run number. The gate defaults off (variable unset), so a master push builds and publishes dev only until the staging stack and `STAGING_*` secrets exist; set `STAGING_ENABLED` to `true` to turn staging publishing on.
- Refactor the provider release pipeline into a thin caller (`.github/workflows/release-swift.yml`) and a reusable workflow (`.github/workflows/release-provider.yml`, `on: workflow_call`) that encapsulates the whole resolve, build, qualification, signing, R2 staging and publication chain for one environment. The caller routes each trigger to its lanes: a master push runs the `dev` and `staging` lanes in parallel, a `vX.Y.Z` tag runs the `prod` lane, and a dispatch runs the chosen environment. A plain matrix cannot carry each lane's artifact id and digest across the dependent jobs, so each lane is a separate call of the reusable workflow.
- The dev and prod paths are preserved exactly: the same signing, notarization, serialization groups (`release-dev` for dev, a per-run group for prod), version stamping and publication idempotency. prod remains tag-gated — `scripts/resolve-provider-release.sh` refuses prod on any non-tag trigger — so a master push can never reach the production signing identity. Accepted cost: one master push now runs two full build, sign, notarize and publish lanes (dev and staging are different binaries, identity is compile-time), and the staging lane's publication is inert until the `STAGING_*` secrets and the staging coordinator (DBLM-771 infra PR 18) exist.
