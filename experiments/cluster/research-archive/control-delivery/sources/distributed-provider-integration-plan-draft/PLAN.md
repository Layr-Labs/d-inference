# Opt-in distributed provider integration

> Source review: 2026-09-15 · main HEAD `605651bb95d71c1da9bb122107925143e9441973` plus the explicitly pinned working-tree files in `source-pins.json`.

Status: Proposed. Source and architecture only; no implementation, build, network, native execution or current candidate inspection by this review. The full HEAD value is recorded in `source-pins.json`.

The smallest useful delivery is an installed worker-owner command, one configured local owner plus one SSH owner, and a single distributed bridge behind the existing local HTTP application. Then install that same bridge as a provider slot. Do not first generalize the network service or make the Python qualification controller part of startup. Ordinary `start`, `start --local`, model loading and solo scheduling remain the default when `--distributed` is absent.

This follows `docs/design/distributed-cluster-delivery.md`, `distributed-cluster-execution-plan.md` and the later `distributed-peer-owner.md` SSH decision. Source facts below are current-main facts; named additions are proposals. Root reported successful serial O128 physical correctness while this plan was prepared; this review did not independently inspect those outputs and makes no performance or release qualification claim.

## Reusable model/runtime contract

Add a small value-only `ClusterRuntimeCapability` descriptor to `DarkbloomClusterProtocol`, and a bounded installed native-worker metadata command that produces it from the actual compiled model adapter and planning code. This is capability discovery, not readiness, hardware attestation, model verification or a memory permit. It may read bounded metadata; it must not construct a model, touch MLX/GPU or hash payloads on ordinary model scanning.

The descriptor binds protocol/owner/bootstrap ABI versions, native runtime build identity, adapter ID/version, exact runtime model ID, supported artifact/config/manifest identities, and the existing `ClusterWorkerProfile`. It names supported partition kind/selection, serial scheduling, text/greedy/stop behavior, state semantics, speculation support, maximum active requests and worker lifetime/request-count limits. Use a selection produced by the real adapter/Plan constructor; do not duplicate cut or fingerprint math in the provider. Unknown adapter, protocol, bootstrap ABI, shape, quantization, modality or speculation combination refuses explicitly.

The provider keeps a verified `ClusterModelBinding` joining a normal registry model ID to that exact runtime capability, artifact and tokenizer/template files. Reuse `ProviderCoreFoundation.ModelManifest` file roles and hashes, `ModelRuntimeRequirements` and `LocalTokenizerLoader`; do not add a second provider model catalog. The current native ID `registered_qwen35_9b` is not assumed to be the public registry ID. Provider routes under the verified public ID; worker identity/agreements retain the native ID. Tokenizer/config/template/EOS identity must be verified before the tokenizer is used, without loading full weights in the leader.

Initial capability is only the current registered 9B serial whole-layer implementation, exactly two ordered ranks, one active request, prompt <=8192, chunk <=512, output <=128, context <=8320, greedy text, no MTP/prefix reuse. These values come from the existing capability implementation, not CLI family-name heuristics. Worker lifetime remains <=300 seconds and <=16 requests; product orchestration must not remove those limits. Future 27B and Gemma support adds an adapter/capability and qualification, not another ownership service. Existing exact-artifact hardware requirements, including `ModelRuntimeRequirements`, remain intersected with the new capability; distributed mode is not a bypass.

## Saved configuration and command behavior

Use one optional `[cluster] configuration = "/.../clusters/<name>.json"` pointer in `ProviderConfig`; decode absence as nil and omit it on legacy serialization. The referenced, versioned, bounded configuration is written atomically into an owned private directory. `configure` prepares it; only `start --distributed` selects it. No `enabled=true` side effect changes an ordinary start.

| Saved field group | Authority and validation |
|---|---|
| Configuration version, cluster ID, this member ID/role/rank, ordered two-member list | Stable setup identity. Every start creates a fresh membership epoch, owner incarnation, device lease and native request UUID; never persist/reuse a previous execution epoch. |
| Public model binding, adapter/capability ID, exact hashes, profile/partition selection, chunk policy, explicit MTP off | Derived and checked against registry files and installed runtime descriptor. No raw ready-frame base64 or arbitrary claimed request capacity in product configuration. Actual capacity arrives after both real loads. |
| Peer host/user/port, approved host-key file, user-key selection, installed Darkbloom path | Reuse `ClusterSSHConfiguration` validation and fixed remote command. Explicit pin import/verification during configure; no silent trust-on-first-use, key scan acceptance, proxy hooks or copied private key bytes. |
| Local model directory and installed native bundle identity | Each member owns its local paths. Peer request frames cannot select arbitrary paths, executables or environment. Verify post-signing runtime/bundle identities through the existing installed release machinery. |
| Named local JACCL device/topology configuration and approved arithmetic policy | Derive the closed environment and matrix from typed settings. Preserve actual device/GID/resource checks; do not expose arbitrary environment injection. Bootstrap remains authenticated and RDMA fabric remains explicitly trusted, not encrypted. |
| Startup/request/lifetime ceilings | Bounded local policy intersected with capability and originating request budget. No persistent uptime or remote absolute timestamp. |

`darkbloom cluster configure` validates a reviewable local setup and explicit trust pins on each member. It checks installed protocol/capability compatibility and saves configuration; a physical collective result is a separately reported doctor result, not implied by saved settings. It must reject configuration replacement while this user's solo/distributed device use is active or unresolved.

`darkbloom start --distributed --local` is the first integrated leader path, using existing bind/auth/port flags and `LocalEndpoint` discovery. `darkbloom start --distributed --local-endpoint` later uses the same distributed slot for both coordinator and local requests. Reject conflicting `--all`, multiple `--model` selections, unsupported model override, media and MTP-on rather than silently falling back. Missing/invalid cluster setup refuses, with no automatic solo execution of that request.

`darkbloom start --distributed` on a follower enters worker-only mode through the normal process/launchd lifecycle: it performs no coordinator registration or model-capacity advertisement and exposes no inference HTTP endpoint. SSH continues to launch the fixed `darkbloom cluster worker-owner --stdio` process on demand; no new always-on network listener is required. The worker-only service records enabled configuration and actual process identity for status. Owner launch verifies this local mode and the canonical device gate. Ordinary solo startup/load must not race a worker owner or unresolved journal; share the existing process/mode exclusion plus the device admission boundary, rather than relying on the state-file text alone. This shared exclusion is a required implementation/test, not provided automatically by the current native journal.

Persist the explicit distributed choice in `LaunchAgent` arguments, restart/watchdog behavior and scheduled foreground reconstruction. Keep ordinary generated plists byte-compatible absent the option. Cluster owner stdio dispatch must avoid AppKit hosting, stdout banners and update checks; only bounded protocol bytes go to stdout. User-facing status may use normal CLI formatting.

Start performs no silent network/interface edits. The callback bootstrap removes the plaintext startup exchange but not the native RDMA GID requirement. If the configured direct fabric needs an IPv4 alias or other setup, doctor reports the concrete missing prerequisite; any privileged setup/rollback is a separate explicit operation. Never disable the live management route/bridge to make the data path fit.

## Owner/session and serving hookup

Add `DistributedExecutionSession` in ProviderCore's existing `Inference/Distributed` folder. It retains the selected capability/model binding, both endpoints, one bootstrap relay, Pair, tokenizer and bridge. Construction runs on bounded ownership queues, not the provider actor or a pipe callback. It publishes readiness only after both actual loads and exact identity/profile/Plan agreement. Failure withdraws readiness before callbacks, requests native cleanup, and retains unresolved ownership.

The first product topology is one local owner process and one authenticated SSH owner. Add a constrained local-owner constructor alongside `ClusterRemoteWorkerEndpoint`: it launches only the configured installed Darkbloom with the fixed owner argv and reuses the existing private pipe/owner protocol implementation. Do not make the arbitrary transport injection test seam public. This avoids reimplementing bootstrap, durable lease and terminal protocol in a new direct-child controller; the local owner still owns its native worker and kernel-bound bootstrap socket. The public `ClusterWorkerEndpoint` interface stays unchanged.

Between requests, a session approaching the capability lifetime/request-count ceiling stops admitting, drains, shuts down, waits for native cleanup AND both device-release acknowledgments, then may construct a fresh epoch. It never extends a running request, resets its origin, migrates state or accepts an old frame into the replacement group. If cleanup/ACK is unavailable, status is quarantined/unresolved and no restart acquires new work. The current journal intentionally lacks general orphan-process recovery; do not delete it, infer absence from SSH exit or automatically manufacture a new epoch. Recovery remains a separate, explicitly proved operation.

For the first local HTTP path, add a small `DistributedModelRegistry` exposing the existing acquire/tokenizer/catalog closures to `makeLocalInferenceApplication`. Acquire returns `AcquiredModel(tokenizer: ..., container: nil, isVLM: false, engineV2Bridge: ..., releaseToken: ...)`. Its reservation prevents idle teardown during a stream; native request ownership remains the engine/Pair lease. Reuse existing auth, upload limits, SSE, errors, template handling and `LocalEndpoint.writeInfo` only after actual bind. Do not fork `MLXOpenAIService` or create a second server protocol.

For coordinator integration, factor `ProviderLoop.ModelSlot` backing into explicit local-model and distributed-session payloads with shared bridge/tokenizer/model metadata. Preserve the existing local initializer and calculations. Update local-only container users (MTP upgrade, vision preparation, wedge rebuild, local memory re-slicing) to require the local payload; the distributed payload reports unsupported capability or closes/rebuilds a fully retired group. Do not install a dummy `ModelContainer`, dummy `SlotSizingSnapshot` or falsely measured zero-byte model. Review every `modelSlots` reader before promotion.

Add a small owner-slot accounting policy to `EngineV2Runtime` / bridge capacity construction. The distributed slot reports one concurrency slot, real aggregate named request capacity and the profile token limits, with actual admitted commitment held until retirement. Local fleet-KV clamps apply only to local slots. Owner capacity is not a bytes-per-token estimate; never divide named recurrent/boundary allowances by an invented rate. Until idle/active/unavailable token-budget mapping is checked against coordinator admission, keep coordinator registration disabled for this backend. Set zero cold-load availability for other models while the device is exclusively assigned to this cluster. Supporting members advertise no second copy of the allocation.

## Deadlines and external TTFT

Preserve the existing chain for coordinator requests: frame `receivedAt` / `RequestProfileBuilder.continuousAnchor` -> `FirstContentDeadline` -> bridge -> `DistributedRequestDeadlineContext` -> PipeOwner -> Pair. Engine queue wait, tokenizer/acquire delay and admission must consume the originating budget. The current pipe adapter floors bounded durations and clamps to profile/worker lifetime. Remote endpoint computes remaining duration at actual send; follower derives its own monotonic deadline and charges its own queue. No Mac's uptime crosses the host boundary.

For direct HTTP, add one request-local profile/receipt context to the existing `LocalChatUploadResponder` -> `serviceForTemplateControls` -> scheduler -> bridge chain. Capture it at responder entry before `collectBody`, and only use it for distributed origin/accounting when opted in. Do not reuse a profile across requests or accept a client header as a trusted OpenRouter origin. Preserve optional nil behavior for existing local/solo callers. If HTTP first-content policy is explicitly configured, derive its deadline once from this local origin and the actual prompt-token policy; whole-generation timeout is separate and remains live after the first token.

An external streaming client records its own monotonic request-send time and first received actual content delta, excluding headers, SSE comments, role-only events and uncommitted drafts. It retains completion, errors, cancellation and deadline margin per request. Reuse the live OpenAI-compatible endpoint with matched tokenizer/template/request/greedy settings and report server spans separately. Sending directly to the local/provider endpoint measures that path, not OpenRouter or the coordinator path. A test through the coordinator is separately required; a genuine OpenRouter origin can only be established by that external caller or a separately trusted upstream contract.

The stated 8,192-token first-content allowance is 18.192 seconds under the delivery plan's 10 seconds + 1 ms/prompt-token policy, with the existing coordinator's effective margin retained. Do not infer success from internal prefill TPS or a median. Keep every miss and compare the fastest correct eligible solo path. No percentile exception is assumed.

`projectFirstToken` remains `.unbounded` until a measured conservative end-to-end owner envelope is supplied. Bridge prediction currently activates only when policy permits and its isolated sample is initialized; absolute deadline checks remain independent. Do not seed fabricated local rates, mark projection unavailable as a pass, or turn projection off to make distributed coordinator serving appear eligible. Start with clearly labeled local measurement; implement and qualify the measured transfer/control projection before claiming coordinator deadline admission support.

Secrets and raw prompt/state data do not belong in status. Existing `DaemonStateFile` freshness and `ProcessIdentity` checks remain; stale or absent remote data is unknown, not ready.

`cluster doctor` performs static checks by default. Explicit `--live` may use a fresh bounded owner session for physical link/collective checks only when no conflicting work/journal exists, and must complete actual cleanup/release before reporting pass. Current owner protocol has no status-query verb: do not pretend a new `ClusterRemoteWorkerEndpoint` is a read-only query, since it opens/launches a worker. Start with read-only local saved/live snapshots; an authenticated remote status helper, if needed, is a fixed bounded installed command reusing the same SSH trust configuration, with no model launch, lease mutation or generic RPC.

The next implementation should complete stages 1–3 as one runnable vertical slice, then stage 4 and operator lifecycle. Keep source/native correctness, live serving, predictive deadline eligibility and measured performance as separate evidence. No public capability is inferred solely from successful configuration, one correctness request or the lookahead source overlay.
